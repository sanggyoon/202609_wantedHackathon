## 1. 아키텍처 — 프론트/백엔드 분리

**결정.** Next.js(프론트) + FastAPI(백엔드)를 분리한 모노레포.

**트레이드오프.**

- 분리: 역할·배포 단위가 명확하고 백엔드를 파이썬으로 둘 수 있음. 대신 서비스가 2개(운영 포인트 증가).
- 풀스택(Next 단일): 배포 단순하나 AI 로직을 파이썬 생태계로 못 가져감.

**근거.** 중재 로직(프롬프트·LLM 호출·판정)이 제품의 핵심이고, 이는 파이썬에서
가장 잘 다뤄짐. 프론트/백 분리 비용보다 이득이 큼.

## 2. 백엔드 — Python + FastAPI

**프로젝트 특성.**

- 핵심 워크로드가 LLM 중재 호출이다. 사건 하나에 대질 질문·판정 등 LLM 왕복이
  여러 번, 각 호출이 수 초 → CPU가 아니라 **네트워크 대기(I/O-bound)** 가 지배적.
- 팀에 주니어가 섞여 있고 기간은 2주.

**결정.** Python + FastAPI.

**왜 Python인가.** 승부처가 "중재 품질"이고 그건 LLM 오케스트레이션·프롬프트·
판정 파싱/평가 로직에 달렸다. 이 영역의 SDK·레퍼런스·디버깅 자료가 파이썬에
가장 성숙 → 주니어가 막혔을 때 빠져나올 길이 많다. (TS에도 SDK는 있으나 예제·
커뮤니티 자료의 두께가 파이썬에 못 미침.)

**왜 FastAPI인가 (다른 파이썬 프레임워크를 배제한 이유).**

- **vs Flask:** Flask는 동기가 기본이라 수 초짜리 LLM 호출이 워커를 통째로
  점유 → 동시 요청 처리에 불리. 비동기·입력검증·문서화를 전부 수동으로 붙여야 함.
  FastAPI는 async 네이티브라 LLM 응답을 기다리는 동안 다른 요청을 흘려보낸다
  (이 프로젝트의 I/O-bound 성격과 정확히 일치).
- **vs Django/DRF:** ORM·admin·auth 배터리가 강점이지만, 우리 백엔드는
  "LLM을 호출하는 얇은 API"라 그 대부분을 안 쓴다 → 오버킬. 무겁고 async가
  후발이라 학습·설정 비용만 커져 2주엔 마이너스.
- **"더 가벼운 걸 써야 하지 않나":** FastAPI 자체가 이미 마이크로 프레임워크다.
  더 가벼운 선택(bare ASGI·Flask)은 async·검증·문서를 직접 구현해야 해 **총비용이
  오히려 커진다**. 우리 규모(2주·얇은 API·I/O-bound)엔 FastAPI가 "가벼움과 기본기"의
  균형점.

**프로젝트에 주는 실이득.** ① async로 I/O-bound에 맞음, ② Pydantic 타입 검증이
잘못된 입력을 자동 차단(주니어 실수 방어), ③ 자동 OpenAPI 문서(`/docs`)로
프론트-백 API 계약이 코드에서 바로 나와 4명 병렬 작업·온보딩이 빨라짐.

## 3. 프론트엔드 — Next.js

**프로젝트 특성.** 제품의 성장 동력이 "판결·합의 결과를 **링크로 공개 공유**"다
(SEO·결과 카드 공유가 핵심, 비로그인 공개 면 존재).

**결정.** Next.js 16 (standalone 빌드).

**근거 (프로젝트 연결).**

- 공유 링크가 카톡·SNS에 붙을 때 **OG 카드 미리보기**(제목·과실비율 썸네일)가
  클릭·확산을 좌우한다 → 서버에서 메타태그·OG 이미지를 렌더해야 함.
- **순수 CSR SPA(CRA·Vite)를 배제한 이유:** 초기 HTML이 비어 있어 크롤러·미리보기
  봇이 내용을 못 읽음 → 공유 카드가 안 뜬다. 이건 제품 핵심(공유)과 정면 충돌.
- Next는 SSR/SSG + 동적 OG 이미지 생성이 표준 기능이라 "공유되는 결과 페이지"를
  자연스럽게 만든다. (Remix도 가능하나 배포 표준·standalone·레퍼런스 두께에서
  Next가 주니어 친화적.)
- 부수 이점(핵심 아님): React 인력 풀이 넓어 검색·충원이 쉬움.

## 5. CI/CD — GitHub-hosted 빌드 + GHCR + SSH 배포

**결정.** PR엔 CI(lint·build), `main` 머지 시 GitHub-hosted 러너가 이미지를
빌드해 **GHCR**에 push → **SSH로 서버 접속**해 pull·재기동.

**대안: self-hosted runner(서버에 러너 상주).**

**트레이드오프.**
| | GitHub-hosted + SSH (채택) | self-hosted runner |
|---|---|---|
| 서버 부담 | 빌드는 클라우드, 서버는 pull만 | 빌드가 서버 리소스 점유 |
| 시크릿 | SSH 개인키 + GHCR pull PAT 관리 | 시크릿 최소(러너가 곧 배포) |
| 보안 | 서버에 러너 미상주(표면 작음) | 러너 뚫리면 서버 노출, fork PR 위험 |
| 빌드 속도 | 캐시 재구성(GHA 캐시로 완화) | 서버 레이어 캐시로 빠름 |

**근거.** 서버에 상시 러너를 두지 않아 공격 표면이 작고 운영이 단순.
빌드/실행 환경이 분리돼 서버는 "받아서 띄우기"만 함. SSH 키·PAT 관리
부담은 시크릿 6개로 감당 가능한 수준.

## 6. 데이터베이스 — Supabase Cloud (Postgres 관리형)

> 2026-09-08 수정: 최초엔 "자체 서버 Postgres에 새 DB"로 결정했으나(하단 이전 근거 참고),
> **프로젝트 존속 기간이 확정**되며 번복함. 아래가 현재 결정.

**프로젝트 특성.** 데이터 모델이 **아직 미확정**(사건·진술·판정·합의 구조가
개발하며 바뀔 것). 그리고 이 프로젝트는 **해커톤 기간(3주)만 운영하고 종료**한다 —
지속 서비스로 이어가려면 LLM API 비용 또는 로컬 LLM용 GPU 리소스 부담이 발생하는데,
그 부담을 계속 질 계획이 없기 때문. 종료 시점엔 데이터만 백업하고 인프라는 폐기한다.

**결정.** 자체 서버에 새 Postgres를 세우는 대신 **Supabase Cloud**(관리형 Postgres +
Auth + Storage)를 사용한다.

**대안과 트레이드오프.**

- **자체 서버 Postgres에 새 DB (기각):** 서버에 이미 Postgres가 떠 있어 비용은 0이지만,
  "프로젝트 종료 시 폐기"라는 수명 주기와 맞지 않음 — 3주 쓰고 버릴 것에 백업·보안·
  격리(전용 유저/DB) 운영 부담을 새로 얹는 건 낭비. 종료 후 정리(DB drop, 유저 삭제,
  볼륨 정리)도 수작업으로 남는다.
- **Supabase Cloud (채택):** 프로젝트 종료 시 Supabase 프로젝트를 데이터 백업 후
  **삭제 한 번으로 정리 끝** — 서버에 아무 흔적도 안 남긴다. Auth·Storage가 내장돼
  있어 "미해결 — 인증 방식" 항목(§ 미해결 참고)도 자체 구현 없이 커버 가능. 대신
  무료/저가 티어의 사용량 제한과 외부 서비스 의존이 트레이드오프.

**근거.** 수명이 명확히 짧고(3주) 종료 후 지속 운영 계획이 없는 프로젝트에는, 자체
인프라를 새로 짓는 것보다 완전 관리형을 쓰고 끝나면 프로젝트째 지우는 쪽이 총비용
(구축 + 운영 + 폐기)이 낮다.

**왜 여전히 PostgreSQL(=Supabase) 계열인가.** 사건 1—N 진술, 사건 1—1 판정, 사건 1—N
배심원 투표처럼 데이터가 본래 관계형이고, 판정 원문·LLM 출력처럼 스키마가 흔들리는
부분은 JSONB로 유연하게 담을 수 있어 모델 미확정 상황에 맞다는 기존 근거는 그대로
유효함 — Supabase도 Postgres이므로 이 이점을 동일하게 가져감.

**후속 작업.** Supabase 프로젝트 미생성(2026-09-08 기준) → 다음 진행 시 프로젝트
생성, 연결 문자열을 백엔드 `.env`(커밋 안 됨)에 배선 필요.

## 10. DB 마이그레이션 도구 — Supabase CLI (`supabase db push`)

> 2026-09-12 수정: 최초엔 "Supabase GitHub 연동이 `main` push 시 자동 적용"으로 결정했으나,
> **그 기능이 무료 플랜에서 동작하지 않음을 확인**해 적용 방식만 번복함. 마이그레이션 형식
> (`supabase/migrations/*.sql`)과 Alembic 기각 판단은 유지. 아래가 현재 결정이며, 번복 경위는
> "발견 경위"에 기록.

**결정.** Alembic(SQLAlchemy 기반) 대신 **Supabase CLI**로 `supabase/migrations/*.sql`을
관리하고, **사람이 `supabase db push`를 실행**해 원격 DB에 적용한다.

### 발견 경위 — 자동 적용은 동작하지 않았다

GitHub 연동을 켜면 `main` push 시 Supabase가 마이그레이션을 자동 적용하고 PR마다 Preview
Branch를 만든다고 보고 채택했으나, **두 기능 모두 Branching에 속하고 Branching은 Pro 플랜
이상**이다. 무료 플랜에서는 연동을 켜도 `supabase/` 디렉터리를 스캐폴딩해주는 것까지가 전부다.

그 결과 **2026-09-10 연동 시점부터 09-12까지 마이그레이션이 한 번도 적용되지 않았다.**
`init.sql`(`pgcrypto` 확장 한 줄)뿐이어서 아무도 눈치채지 못했다. 09-12에 스키마 PR을 머지한
뒤 확인하는 과정에서 발견했다 — `supabase_migrations.schema_migrations` 테이블 자체가
존재하지 않았고(= 적용 이력 0), `public` 테이블이 0개였다.

문제를 가린 우연이 하나 있었다. `pgcrypto`는 조회 시 이미 활성 상태였는데, 이는 `init.sql`이
적용된 증거가 아니라 **Supabase가 새 프로젝트에 기본 제공하는 것**이었다. 마이그레이션이
의도한 것과 같은 확장이라 "적용된 것처럼" 보였다.

**교훈.** 마이그레이션 적용 여부는 결과 객체의 존재로 판단하지 말고
`supabase_migrations.schema_migrations`로 판단한다. 이 테이블은 적용이 한 번이라도
일어나면 생성되므로, 부재 자체가 "한 번도 적용 안 됨"의 확정 증거다.

**대안과 트레이드오프.**

| | **Alembic (기각)** | **Supabase GitHub 연동 (채택)** |
|---|---|---|
| 마이그레이션 작성 언어 | Python (SQLAlchemy 모델에서 자동 추론) | 순수 SQL 파일 |
| 적용 위치 | 백엔드(FastAPI)에 라이브러리로 편입 | Supabase 자체 기능 (CLI + GitHub App) |
| 적용 방식 | 서버에서 `alembic upgrade head` 직접 실행 — 배포 파이프라인(`deploy.yml`)에 마이그레이션 스텝을 새로 추가해야 함 | 로컬에서 `supabase db push` 수동 실행 (무료 플랜에서 자동 적용 불가) |
| PR별 격리 테스트 | 없음 (직접 구현 필요) | 없음 — Preview Branch는 Pro 플랜 전용이라 이 프로젝트에선 사용 불가 |
| 백엔드 요구사항 | SQLAlchemy ORM을 실제로 도입해야 함 (현재 백엔드엔 DB 라이브러리 자체가 없어 처음부터 새로 얹는 작업) | 없음 — ORM 없이 raw SQL/Supabase 클라이언트만으로도 가능 |
| 학습 곡선 | ORM 모델 설계 + Alembic 커맨드(`revision`, autogenerate 특이사항) | SQL 파일 작성 — 별도 도구 학습 거의 불필요 |
| 이식성 | 어떤 Postgres에도 동일 동작, Supabase 종속 없음 | SQL 대부분은 이식 가능하나, `anon`·`authenticated` 롤에 대한 `revoke`는 Supabase 전용 |
| 신뢰 표면 | 없음 (백엔드 내부 도구) | 개발자 로컬에 Supabase access token + DB 비밀번호 보관 |

**근거.** 이 프로젝트 맥락에서 Alembic의 비용이 이득보다 크다고 판단:

- 백엔드에 DB 라이브러리가 아직 전혀 없는 상태라, Alembic 채택은 "있는 걸 활용"이 아니라
  SQLAlchemy부터 새로 얹는 작업. 반면 Supabase 연동은 추가 백엔드 의존성이 0.
- 팀에 주니어가 섞여 있음(§2 근거와 동일 맥락) — ORM 모델 → 마이그레이션 자동생성이라는
  추상화 단계보다 SQL 파일을 직접 보고 쓰는 쪽이 진입장벽이 낮음.
- §6에서 Supabase Cloud를 택한 근거("관리형으로 운영 부담 최소화, 종료 시 통째로 삭제")와
  방향이 일치함 — 백엔드 쪽에 마이그레이션 인프라를 쌓지 않는 편이 동일 철학.
- ~~이미 동작 중인 CI/CD 파이프라인에 마이그레이션 실행 스텝을 끼워 넣지 않아도 됨~~
  → **이 근거는 더 이상 성립하지 않는다.** 자동 적용이 안 되므로 사람이 `db push`를 하거나
  파이프라인에 스텝을 추가해야 하며, 후자를 택하면 Alembic을 기각할 때 든 단점을 그대로 진다.
  남은 우위는 "백엔드 의존성 0"과 "SQL 직접 작성"이고, 3주 일정에서는 이 둘만으로도 Alembic
  도입 비용(SQLAlchemy 신규 편입)을 넘지 못한다고 판단해 결정 자체는 유지함.

**현재 운영 방식.** 마이그레이션 파일을 추가한 뒤 다음을 실행한다. 로컬 Docker 스택은 필요
없다 — 원격에 직접 적용하는 명령이다.

```bash
supabase db push              # 미적용 마이그레이션만 순서대로 적용
supabase migration list       # 로컬·원격 버전 일치 확인
supabase db diff --linked     # "No schema changes found"면 drift 없음
```

**주의 — 머지만으로는 아무 일도 일어나지 않는다.** `main`에 머지해도 DB는 바뀌지 않는다.
마이그레이션을 추가한 사람이 `db push`까지 해야 한다. 이 단계를 빠뜨리면 코드와 스키마가
어긋나고, 다른 팀원은 "내 쪽에서만 안 되는" 증상을 만난다.

**미해결 — 자동화 여부.** 사람이 매번 실행하는 방식은 잊기 쉽다. `deploy.yml`에
`supabase db push` 스텝을 추가하면 해소되지만, 그러면 위에서 말한 "파이프라인 무수정" 이점이
완전히 사라지고 CI에 Supabase access token·DB 비밀번호를 시크릿으로 넣어야 한다.
착수 여부는 팀 논의 필요.

# CI/CD 플로우

두 개의 파이프라인으로 나뉜다.

- **CI** (ci.yml) — PR마다 "깨졌는지" 검증. 배포 안 함.
- **CD** (deploy.yml) — `main` 머지 시 "빌드→푸시→배포".

## 전체 그림

```
  개발자 로컬
    │  git push (feature/*)
    ▼
  GitHub ── PR 생성 ──▶ [CI: ci.yml]  (GitHub-hosted 러너)
    │                     ├─ backend: ruff lint + import 검증
    │                     └─ frontend: npm ci + lint + build
    │                          └─ ✅ 통과해야 머지 가능(main 보호규칙)
    │  리뷰 승인 + squash merge
    ▼
  main 갱신 ──▶ [CD: deploy.yml]  (GitHub-hosted 러너)
    │  job1  build-and-push
    │    ├─ backend 이미지 빌드 → GHCR push (:latest, :<sha>)
    │    └─ frontend 이미지 빌드 → GHCR push (:latest, :<sha>)
    │  job2  deploy  (job1 성공 후)
    │    └─ SSH 접속 → 서버에서:
    │          docker login ghcr.io (CR_PAT)
    │          IMAGE_TAG=<sha> docker compose pull
    │          docker compose up -d
    │          docker image prune -f
    ▼
  우분투 서버
    Nginx(443) ─ /     → frontend:3000
                └ /api → backend:8000 → Supabase Cloud(관리형 Postgres)
```
