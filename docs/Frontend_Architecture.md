## 1. 목적과 문서 우선순위

이 문서는 와이어프레임과 프론트엔드 구현의 화면 구조, 책임 분리, 상태 관리 및 작업 순서를 정의한다.

- 제품 동작과 문구는 PRD를 따른다. 과거 ADR의 판결·과실비율·공개 검색·로그인 전제는 적용하지 않는다.
- 시각 규칙은 디자인 시스템을 따른다.
- 기술 기반은 기존 Next.js 프로젝트를 유지한다.
- 이 문서의 제안 API 및 미정 정책은 백엔드 구현 사실이나 확정된 제품 요구사항으로 간주하지 않는다.

## 3. 확정 레이아웃

- 모든 화면의 컨테이너는 **바깥 너비 최대 768px**, 가운데 정렬한다.
- 좌우 패딩은 각 16px이며 최대 너비 안에 포함한다.
- 뷰포트 768px 미만에서는 A/B 카드를 세로로 배치한다.
- 뷰포트 768px 이상에서는 같은 768px 컨테이너 안에 동일 너비 2열로 배치한다. 리포트만 별도로 넓히지 않는다.
- 최대 너비에서 내부 공간은 736px이며, 카드 간격 16px을 제외하면 카드당 360px이다.
- 두 카드 아래 중재 요약은 전체 열 너비를 사용한다.
- 긴 단어와 URL은 줄바꿈하며 카드가 가로로 넘치지 않게 한다.
- 채팅 입력창과 하단 CTA도 같은 컨테이너 폭에 맞춘다. 입력창 높이와 안전 영역만큼 본문 여백을 확보한다.

## 4. URL과 화면 구분

아래 경로는 프론트엔드 설계 경로다. 사건 작성 시작 시 서버에서 사건 토큰을 발급받는 안을 사용하며, 공유 버튼은 고소장 확정 후 활성화한다. PRD의 흐름도와 FR-05 사이의 발급 시점 표현 차이는 이 방식으로 해석한다. 백엔드 계약 확정 시 초안 사건 생성·만료 규칙을 함께 정한다.

| 경로 | 역할 |
| --- | --- |
| `/` | 서비스 소개와 작성 시작 |
| `/case/[token]` | 작성, 미리보기, 공유·대기, 상대 응답, 최종 리포트, 만료를 사건 상태에 따라 표시 |

작성·사과·맞고소·결과마다 별도 URL을 발급하지 않는다. 미리보기 열기, 카드 펼치기 등의 화면 내부 변화는 로컬 UI 상태로 처리한다. 새로고침 시 서버의 사건 상태로 다시 진입한다.

개발용 화면 미리보기가 필요하면 별도 개발 전용 진입점을 두고 가상 데이터를 사용한다. 운영 사건 링크의 상태를 쿼리 문자열로 조작하는 기능은 제공하지 않는다.

## 5. 사건 상태와 화면 전환

서버 사건 상태와 브라우저 UI 단계를 구분한다. `preview`, `editing`, `submitting` 등은 서버 사건 상태를 새로 만들지 않는 UI 단계다.

| 서버 상태 | 화면 | 주요 동작 |
| --- | --- | --- |
| `DRAFT` | A의 대화·요약 수정·고소장 미리보기 | 고소장 확정 |
| `AWAITING_RESPONSE` | A: 공유·대기 / B: 고소장 열람·응답 선택 | 링크 공유, 사과 또는 맞고소 선택 |
| `COUNTER_DRAFT` | B의 대화·요약 수정·맞고소 미리보기 | 맞고소 제출 |
| `COUNTER_COMPLETED` | A/B 카드와 중재 리포트 | 상세 펼치기 |
| `APOLOGY_DRAFT` | 직접 작성 사과문과 미리보기 | 사과문 제출 |
| `APOLOGY_COMPLETED` | 사과 카드와 종결 리포트 | 내용 열람 |
| `EXPIRED` | 만료 안내 | 새 사건 시작 |

작성 중인 사람 이외의 방문자에게는 대기 화면을 표시한다.

**확정·구현됨 (2026-09-17).** 작성 권한은 사건 생성 시 발급한 `writer_token`을 `X-Writer-Token`
헤더로 보내 확인하고, 브라우저 localStorage에 보관한다. 같은 브라우저의 다른 탭에서는 A로
인식되고 다른 기기에서는 B로 보인다. 화면은 서버가 준 `status`·`viewer_role`·`available_actions`로
정한다(`features/case/caseStage.ts`).

완료 화면에는 편집·재제출 CTA를 두지 않는 것을 초기안으로 사용한다. 실제 재제출 차단은 서버 책임이며 답변 수정 정책 확정에 따라 조정한다.

## 6. 화면 구성

| 화면 | 핵심 구성 | 주요 행동 |
| --- | --- | --- |
| 시작 | 한 줄 소개, 서비스 설명, 법적 효력 없음 안내 | 귀엽게 고소장 만들기 |
| A 대화 | 대화 목록, 파악한 정보, 입력창, 응답 대기 표시 | 답변, 이전 답변 수정, 요약 확인 |
| A 미리보기 | 죄명, 사건·감정·바라는 점, 관점 안내 | 수정, 확정 |
| 공유·대기 | 확정 고소장, 공유 안내, 답변 대기 상태 | 공유, 링크 복사, 상태 확인 |
| B 열람 | 핵심 요약, 고소장 펼치기, 비판결 안내 | 사과하기, 맞고소하기 |
| B 맞고소 | A의 요약 참조, B 대화와 입력창, 미리보기 | 요약 수정, 제출 |
| 맞고소 결과 | A/B 동등한 카드, 공통점·차이·감정·대화 시작 문장 | 전체 내용 펼치기 |
| 사과 작성 | A의 요약, 사과문, 이해한 내용·약속 선택 입력 | 미리보기, 사과문 보내기 |
| 사과 결과 | A 요약, B 원문 사과 카드, 종결 요약 | 결과 열람 |
| 만료·잘못된 링크 | 사건 내용 없는 안내 | 새 사건 시작 |

`종결`은 B의 응답 흐름 완료를 뜻한다. A의 사과 수락·거절 기능을 추가하지 않는다. 사과문을 AI가 대신 작성하는 CTA도 두지 않는다.

## 7. 폴더 구조와 책임

2026-09-19 기준 실제 구조다. 하위 폴더를 두지 않고 기능 폴더에 파일을 평평하게 둔다.

```text
frontend/src/
  app/
    layout.tsx                  # 한국어, 공통 메타데이터·viewport·전역 스타일
    globals.css                 # 디자인 토큰과 기본 스타일
    page.tsx                    # 제품 홈
    case/[token]/page.tsx       # 실제 사건 화면 진입 (loading·error 파일은 없음)
    wireframe/page.tsx          # 가상 사건 체험
  components/
    ui/index.tsx                # Button, Heading, Notice, Toast
    layout/AppShell.tsx         # 헤더·푸터·개발용 탭 슬롯
  features/
    case/
      LinkedCaseScreen.tsx      # 조회·단계 분기·제출 처리
      caseStage.ts              # 상태×역할×행동 → 단계 판정, 실패 판정
      ADraftFlow.tsx            # A 대화 → 검토 → 접수
      BResponseFlow.tsx         # B 소환장 → 사과/맞고소 → 제출
      ShareCaseLink.tsx         # 실제 링크 복사·공유
      writerSession.ts          # 작성 권한 보관 (localStorage)
      CreateCaseButton.tsx      # 사건 생성
      StartScreen.tsx           # 시작화면 1/2/3
      CaseController.tsx        # 체험(/wireframe) 전용 화면 전환
      ShareSelectScreen.tsx     # 미사용 — 공유 선택 단계 제거 후 남은 파일
      screens/                  # SummonsSent, SummonsArrived, Waiting, CounterclaimResult, ApologyResult, CaseGone
    conversation/
      LiveConversationScreen.tsx, useConversation.ts, ConversationScreen.tsx, types.ts
    report/
      StatementCard.tsx, StatementSummary.tsx, PreviewScreen.tsx, ApologyScreen.tsx,
      MediationSummary.tsx, MediationReport.tsx, EmotionWarpImage.tsx, types.ts
  lib/
    api/                        # cases, conversation, mediation, cardSummary, emotionWarp
  mocks/Wireframe.tsx           # 체험용 가상 사건 데이터
```

사건 모델 타입은 `features/case/types.ts`가 아니라 `lib/api/cases.ts`에 있다.

경로 파일은 화면을 조합하고, 기능별 폴더는 제품 동작을 담당한다. 공통 UI는 사건 상태나 API를 직접 알지 않는다. A/B 대화와 카드는 역할·데이터를 인자로 받아 재사용한다.

## 8. 렌더링과 상태 관리

### 와이어프레임의 의존성 규칙

- `app → mocks의 조합 컴포넌트 → case 컨트롤러 → 대화·리포트 화면 → 공통 UI` 방향으로만 참조한다.
- 컨트롤러는 화면 전환과 완료된 결과를 관리한다. 입력과 편집은 개별 화면이 소유한다.
- `features`, `components`는 `mocks`를 직접 import하지 않는다. 데이터와 질문은 props로 주입한다.
- 위 규칙은 `/wireframe` 체험 흐름에 대한 것이다. 가상 화면 선택기는 이 경로에만 제공한다.
- 실제 사건 URL·저장·공유·만료는 2026-09-17에 연결됐다(`app/case/[token]`, `LinkedCaseScreen`).
- 입력값은 미리보기에 그대로 반영한다. 중재 정리는 실제 API 결과를 쓴다 — 체험은 요청해서,
  실제 사건은 저장된 리포트를 표시만 한다.

- 공통 레이아웃과 정적 소개 영역은 서버 렌더링을 기본으로 한다.
- 채팅, 입력, 미리보기 수정, 공유, 사건 상태 전환은 필요한 영역에 Client Component를 사용한다.
- 단순 UI는 React 상태, 여러 단계가 연결된 대화·작성은 reducer로 관리한다. 초기에는 전역 상태 라이브러리를 추가하지 않는다.
- 서버 데이터는 API 계층을 통해 조회하며 사건 상태의 최종 권위는 서버에 둔다.
- 펼침·모달·작성 중 텍스트와 제출 중 상태는 해당 화면이 소유한다.
- 원문 대화와 임시 사과문은 메모리에만 보관한다. localStorage, sessionStorage, URL에 넣지 않는다. 결과 생성 후 원문 상태를 비운다.
- 새로고침·이탈 시 임시 내용이 사라질 수 있음을 안내한다. 브라우저 이탈 경고만으로 복구를 보장하지 않는다.
- A 역할의 로컬 표시는 UX 힌트이며 작성 권한의 증거로 사용하지 않는다. 실제 작성 권한은 서버가 검증해야 한다.
- 대기 화면은 재진입·포커스 복귀·수동 새로고침으로 상태를 갱신한다. 자동 폴링은 API와 주기 합의 후 추가하며 완료·만료 시 중단한다.

## 9. API 연결 경계

> 2026-09-14: 아래 계약 목록에 실제 경로·요청·응답·오류 코드가 부여됐다. **`docs/API_Design.md`가 기준 문서다.** 이 절은 "프론트가 무엇을 필요로 하는가"의 기록으로 남긴다.

현재 문서의 백엔드 진행 기록은 health API까지 설명한다. 아래 기능은 필요한 계약 목록이며 기존 구현으로 가정하지 않는다.

| 필요한 계약 | 프론트가 필요한 결과 |
| --- | --- |
| 사건 작성 시작 | 사건 토큰, 상태, 작성 권한 처리 방식 |
| 사건 조회 | 상태, 열람 가능한 카드·리포트, 만료 시각, 가능한 행동 |
| AI 대화 | 응답 또는 스트림, 파악한 필수 정보, 요약 가능 여부 |
| 고소장 확정 | 저장된 고소 카드와 답변 대기 상태 |
| 응답 방식 선택 | 사과·맞고소 작성 상태, 동시 작성 충돌 처리 |
| 맞고소 제출 | 저장된 B 카드와 최종 리포트 또는 생성 중 상태 |
| 사과 제출 | 직접 작성 원문과 종결 리포트 또는 생성 중 상태 |

운영 요청은 같은 도메인의 `/api`를 기준으로 한다. 로컬 개발에서는 백엔드 연결을 위한 프록시 또는 공개 가능한 API 주소 설정을 구현 시 정한다. 백엔드 `.env`나 비밀 키를 프론트 코드로 가져오지 않는다.

실제 경로, 요청·응답 형식, 스트리밍 방식, 오류 코드, 작성 권한, 중복 제출 방지 및 리포트 비동기 생성 정책은 백엔드와 계약한다. 화면 컴포넌트에서 직접 fetch를 흩어 쓰지 않고 어댑터를 통해 가상 데이터와 실제 API를 교체한다.

사건 응답을 공개·공유 캐시에 저장하지 않는다. 서버 렌더링을 적용할 경우에도 사건별 캐시와 메타데이터 처리 방식을 명시적으로 점검한다.

## 10. 디자인 시스템 적용

- 색상·간격·라운드·레이어는 `globals.css` 토큰으로 선언하고 Tailwind에서 사용한다.
- 기본 배경은 문서의 단순 그라디언트 안인 `linear-gradient(-7deg, #FAFAFA 26%, #F0EFEE 84%)`로 통일한다.
- 기본 UI는 Pretendard, 포인트 서체는 제목·죄명 등 제한된 위치에 사용한다. 포인트 서체 파일 경로와 사용 조건은 적용 전에 확인한다.
- 기존 Geist·Arial·자동 다크모드 설정을 디자인 시스템으로 교체한다. 다크모드는 현재 설계 범위에 없다.
- 아이콘 라이브러리는 아직 없다. 텍스트 글리프(↗ ↑ ✓)와 PNG를 쓴다. Lucide는 도입 후보다.
- A/B 전용 색은 아직 토큰이 없으므로 시각 작업에서 추가 확정한다. 색뿐 아니라 역할 레이블도 함께 표시한다.
- 터치 영역은 최소 48×48px, 하단 안전 영역을 확보한다.
- 채팅 응답 대기, 스트리밍, 오류는 각각 구분한다. 스트리밍 구현 여부는 백엔드 계약에 따른다.

## 11. 공통 예외와 접근성

| 상황 | 처리 |
| --- | --- |
| 초기 로딩 | 실제 사건 화면은 한 줄 상태 텍스트. 스켈레톤은 `/wireframe`의 '심리 준비' 예시 화면에만 있다 |
| AI 응답 대기 | 타이핑 표시, 중복 전송 방지 |
| 생성 실패 | 현재 메모리 입력 유지, 인라인 오류와 재시도 |
| 제출 충돌 | 최신 사건 상태를 다시 조회하고 결과 또는 대기 안내 |
| 만료·잘못된 토큰 | 사건 내용을 표시하지 않는 안내 |
| 공유 기능 미지원 | 링크 복사 제공, 복사 실패 시 직접 선택 가능한 링크 |
| 안전상 생성 중단 | 일반 생성 실패와 구분된 안내; 구체 문구는 정책 확정 후 적용 |

입력에는 레이블을 연결하고 오류 원인을 텍스트로 표시한다. 모달은 키보드 포커스 진입·복귀를 지원한다.

**현재 코드와 다른 점 (2026-09-19, 후속 과제).**

- 채팅 화면은 새 턴·대기·오류마다 **항상 맨 아래로 스크롤한다.** 과거 대화를 읽는 중인지 보고
  억제하는 처리는 없다.
- `body.chat-open` 규칙이 `.screen > .notice`를 숨긴다. 그래서 채팅 중에는 비저장 안내와
  **대화 오류 문구가 화면에 보이지 않는다.** 오류·안내를 채팅 영역 안으로 옮겨야 한다.
- `prefers-reduced-motion` 규칙이 아직 없다.
- 검색 색인 차단은 사건 페이지뿐 아니라 `layout.tsx`에서 **사이트 전체**에 걸려 있다.

공유 미리보기에는 서비스 소개를 사용하고 사건 본문·감정·사과문을 포함하지 않는다. 사건 페이지는 검색 색인을 차단한다.

## 12. 구현 순서와 검수

1. **설계 기준 적용**: 이 문서를 기준으로 화면 목록, 상태, 공통 UI 역할을 정한다.
2. **기반 UI**: 전역 토큰, 한국어 설정, 서체, 768px AppShell, 버튼·입력·카드를 만든다.
3. **와이어프레임**: 가상 데이터로 시작 → A 작성·공유 → B 응답의 두 분기 → 결과·만료를 연결한다.
4. **반응형·예외 검수**: 375px 모바일, 768px 경계, 1280px 화면에서 컨테이너·카드 배치와 로딩·오류를 확인한다.
5. **API 연결**: 확정된 계약에 맞춰 어댑터를 교체하고 작성 권한·동시 제출·만료를 검증한다.
6. **마무리 검증**: lint와 production build, 두 응답 경로의 수동 동작 검수 및 핵심 상태 분기 테스트를 진행한다.

와이어프레임 단계에서는 동작 확인용 가상 응답임을 개발 화면에서 명확히 표시한다. API 연결 전 실제 공유·서버 저장·7일 만료가 구현됐다고 표현하지 않는다.

검수 시 단일 사건 URL 유지, A/B 동등한 카드 배치, 모바일 입력창 가림 여부, 48px 터치 영역, 요약 수정, 직접 작성 사과문 보존, 원문 영구 저장 부재를 확인한다.
