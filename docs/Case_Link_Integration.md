# 실제 사건 링크 연결 (2026-09-16)

## 구현 범위

- 홈의 시작하기 → POST /api/cases → /case/[token] 이동.
- API 어댑터: frontend/src/lib/api/cases.ts. 생성/조회 요청, 런타임 응답 검증,
  15초 제한, no-store, 원문 서버 오류를 노출하지 않는 오류 변환.
- 로컬 Next 개발 서버에서 /api/cases 경로를 백엔드로 전달.
- 조회 결과의 viewer_role·status·available_actions로 작성 가능 여부 결정.
- 저장 API 연결 (2026-09-17): A 접수(`statement` A), B 사과(`response-type` → `apology`),
  B 맞고소(`response-type` → `statement` B). 단계는 `caseStage`가 status·viewer_role·
  available_actions로 정한다 (`docs/superpowers/specs/2026-09-17-case-link-flow-design.md` §5).
- B의 사과/맞고소 선택은 최종 제출 때 확정한다. 선택만 저장되고 제출이 실패했으면 같은 쪽으로
  이어서 작성한다.
- 제출 실패 시 403·422는 작성 내용을 유지하고, 404·410은 만료/없음 화면, 그 외는 재조회로
  저장 여부를 확인한다. POST는 자동 재시도하지 않는다.
- 완료 사건은 저장된 카드·리포트·사과만 표시한다. 새로운 AI 리포트를 임의로 생성하지 않는다.
- 화면은 체험판(`/wireframe`)과 같은 컴포넌트(`features/case/screens/`)를 쓴다.
- 저장된 A 카드가 존재하고 DRAFT가 아닐 때 작성자에게 링크 복사/공유 제공.
  클립보드 실패 시 직접 선택 가능한 URL, 공유 미지원 시 복사로 대체.
- 404/410은 내용을 제거하고 안내. 일시적인 재조회 실패는 기존 입력을 유지.
- 최초 진입, 포커스 복귀, pageshow, 수동 버튼으로 조회. 자동 폴링 없음.
- 서버 expires_at 도달 시 표시 내용을 제거한다. 만료 판정의 최종 권위는 서버다.
- /wireframe은 기존 가상 사건 체험으로 유지한다. 실제 작성은 /에서 시작한다.

## 작성 권한 보관

- 사건별 writer_token과 expires_at만 localStorage에 보관한다 (2026-09-17 변경).
  sessionStorage는 탭 단위라 A가 자기 링크를 새 탭에서 열면 B로 판정돼, 저장 API 연결 후
  자기 사건에 답변을 확정할 위험이 있었다.
- 이전 버전이 sessionStorage에 둔 값은 첫 조회 때 localStorage로 옮긴다.
- 같은 브라우저의 다른 탭에서는 A로 인식된다. 다른 기기에서는 B로 보인다.
  공용 기기에서는 만료 전까지 권한이 남는다. 사용자 신원 인증 수단은 아니다.
- 작성 권한 검증은 서버의 X-Writer-Token 검사로만 한다.
- public_token만 URL에 넣고 writer_token은 요청 헤더에만 사용한다.
- 대화·카드 초안·사과 원문은 브라우저 저장소에 저장하지 않는다.
- 저장소를 사용할 수 없으면 생성 요청 전에 안내한다. 생성 후 보관 실패 시
  같은 화면에서 발급 응답을 재사용하여 사건을 중복 생성하지 않는다.
- POST는 자동 재시도하지 않는다. 네트워크 실패 시 서버에 빈 사건이 생성됐을 수 있다.
  서버의 생성 멱등성 계약이 없어 새 요청으로 생기는 빈 사건까지 막지는 못한다.
- 사건 페이지의 referrer 정책은 no-referrer. 접근 로그의 토큰 마스킹은 별도 배포 작업이다.

## 남은 연결

- 운영 환경에서 실제 AI로 맞고소 제출 시간 실측 (Nginx `proxy_read_timeout` 60초 대비)
- 접근 로그의 토큰 마스킹 (배포 작업)
- 새로고침 시 작성 중 내용 복구는 하지 않는다 (원문 비저장 원칙, PRD §14 미정)

## 검증 및 실행

- frontend에서 npm test: API/권한 저장소 회귀 테스트 16개 (fetch·storage 대체).
- npm run lint, npm run build 통과.
- 브라우저에서 홈의 시작하기 → 저장 서버 미설정(503) 안내 확인.
- 현재 로컬 설정에 DATABASE_URL이 없어 실제 DB 생성·조회 성공 검증은 미수행.
  토큰/DB 비밀 값은 테스트 로그에 출력하지 않는다.
- backend/.env에 개발 DB의 DATABASE_URL을 설정하고 백엔드를 재시작해야 한다.
  브라우저용 NEXT_PUBLIC_ 변수에 DB 주소나 AI 키를 넣지 않는다.
- 프론트 npm run dev, 백엔드 uv run uvicorn app.main:app --reload --port 8000.
  http://localhost:3000 에서 시작한다.

실DB 연결 후 추가 확인: 시작하기 연속 클릭 시 한 사건만 생성, 새로고침 시 A 유지,
권한 없는 별도 브라우저에서 DRAFT 내용 비노출, 저장된 사건 조회/링크 복사,
만료 사건 410 및 내용 비노출. 운영 DB에 시험 내용을 저장하지 않는다.

### 로컬 Supabase 전체 흐름 검증 (2026-09-17)

`supabase start`(마이그레이션 4개 적용) + `DATABASE_URL=postgresql://postgres:postgres@127.0.0.1:54322/postgres`,
백엔드 local AI 모드. A는 `http://localhost:3000`, B는 `http://127.0.0.1:3000`(출처가 달라 저장소가 분리됨).

| 시나리오 | 결과 |
| --- | --- |
| A 접수 → A 소환장 발송, B 소환장 도착 | 통과. 작성 권한은 localStorage에만 저장, 검토 화면에서 입력한 죄명이 B 요약에 표시 |
| A가 같은 브라우저 새 탭에서 열기 → A | 통과 |
| B 맞고소 선택 → 다시 고르기 → 사과 제출 → 양쪽 화해 성립 | 통과. 보관 기한이 답변 시각 +7일로 갱신 |
| B 맞고소 제출 → 양쪽 양측 대질 | 통과. 각자 자기 카드에 "내가 쓴 고소장", 결과 화면에서 `/api/mediation/report` 호출 없음 |
| 제출 중 백엔드 중단 → 작성 내용 유지 → 재제출 | 통과. "사건 서버에 연결하지 못했어요. 작성한 내용은 그대로 있어요. 다시 제출해주세요." 후 재제출 성공 |
| 이미 제출된 사건에 다른 탭에서 재제출 | 통과. 409 → 재조회 → "이미 제출된 사건이에요. 최신 상태를 보여드릴게요.", 먼저 제출한 사과문만 저장 |

검증 중 발견·수정: 저장된 카드에는 `sourceMode`가 없어 B 소환장 요약에 "현재는 화면 체험용 예시 사건입니다."가
표시됐다. `StatementSummary`에 `demo` prop을 두고 링크 흐름은 `false`를 넘긴다.

주의: Next 개발 서버는 기본적으로 `127.0.0.1` 출처의 개발 리소스 요청을 막는다. 같은 방식으로 B를 재현하려면
`next.config.ts`에 `allowedDevOrigins: ["127.0.0.1"]`를 **임시로** 넣고 개발 서버를 재시작한다(커밋하지 않음).
local AI 모드에서는 맞고소 제출이 즉시 끝나 "정리하고 있어요… (최대 1분)" 버튼 문구는 확인하지 못했다.
