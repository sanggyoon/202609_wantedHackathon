## 1. Next.js 프론트엔드 프로젝트 생성

### 목표
ADR §1~§3의 결정(프론트/백 분리 모노레포, Next.js)에 따라 `frontend/` 디렉토리에 실제 앱을 만드는 것. 아직 저장소에는 `docs/`만 있는 빈 상태였음.

### 준비 — Node.js 환경이 아예 없었음
서버(GMKtec K16, 홈서버)는 이제까지 Docker 기반 서비스만 운영해왔기 때문에 `node`, `npm`이 시스템에 전혀 설치되어 있지 않았다. 확인해보니:
- `node --version`, `npm --version` 모두 command not found
- `nvm`, `fnm`, `volta` 등 버전 매니저도 없음
- 대신 Docker는 이미 설치되어 있었음(v29.7.2)

로컬에서 직접 개발/스캐폴딩을 하려면 Node가 필요하다고 판단해서, Docker 컨테이너로 우회하는 대신 **nvm으로 Node LTS를 직접 설치**하기로 함(이후 팀원들이 로컬 개발 시에도 같은 방식을 쓸 수 있어야 하므로).

```bash
curl -o- https://raw.githubusercontent.com/nvm-sh/nvm/v0.40.1/install.sh | bash
nvm install --lts   # → v24.20.0, npm 11.19.0 설치됨
```

### 실행 — create-next-app
ADR §3 결정(Next.js, App Router, OG 이미지 동적 생성 필요)에 맞춰 아래 옵션으로 생성:

```bash
npx create-next-app@latest frontend \
  --typescript --app --eslint --tailwind \
  --src-dir --import-alias "@/*" --use-npm --no-turbopack
```

- TypeScript: 타입 안정성
- App Router: SSR/동적 OG 이미지가 ADR §3의 핵심 요구사항이라 필수
- Tailwind: 3주짜리 해커톤에서 스타일링 속도를 위한 실용적 선택 (ADR엔 명시 안 됐지만 팀 합의 없이 흔한 기본값으로 채택 — 필요시 팀 논의 후 변경 가능)
- `src/` 디렉토리 + `@/*` alias: 코드 구조 관례

### 문제 1 — 버전 불일치 발견
`create-next-app@latest`가 실제로 설치한 버전은 **Next.js 16.3.4**였는데, ADR §3엔 "Next.js 15"로 못박혀 있었음(Accepted 상태 문서). 임의로 넘어가지 않고 사용자에게 확인:
- 옵션 A: 16 유지 (standalone/App Router/동적 OG 등 ADR이 근거로 든 기능은 16에서도 동일 지원)
- 옵션 B: 15로 다운그레이드 (ADR 정합성 우선)

→ **16 유지**로 결정. 대신 ADR 원문의 "Next.js 15" 표기를 "Next.js 16"으로 수정해서 문서-코드 불일치를 남기지 않았음.

### 실행 — standalone 빌드 설정
ADR §4(Docker 배포)를 위해서는 `output: "standalone"`이 필요. Next 16이 처음 겪는 버전이라(`AGENTS.md`에 "이 버전은 breaking change가 있을 수 있으니 docs부터 확인하라"는 경고가 실제로 있었음) 임의로 넣지 않고 `node_modules/next/dist/docs/01-app/02-guides/building.md`를 직접 확인해서 `output: 'standalone'` 옵션이 16에서도 동일하게 동작함을 검증한 뒤 `next.config.ts`에 반영.

### 검증
```bash
npm run build   # 정상 컴파일, 정적 페이지 생성 확인
ls .next/standalone   # server.js, node_modules, package.json 생성 확인
```

## 2. 배포 설정 — 자체 서버 + nginx-proxy

### 목표
ADR §4/§7(자체 우분투 서버 + Docker Compose + nginx-proxy/certbot)대로 방금 만든 프론트엔드를 실제로 인터넷에 띄우는 것.

### 준비 — 기존 서비스 패턴 조사
새로 아무 패턴이나 만들지 않고, 이 서버에서 이미 돌고 있는 동종 서비스(`WEBportfolio`, `InvestingStratege`)의 `docker-compose.yaml`/`Dockerfile`을 먼저 읽어서 **기존 컨벤션을 그대로 재사용**하기로 함:
- 각 서비스는 `proxy`라는 external Docker 네트워크에 붙고, `VIRTUAL_HOST`/`LETSENCRYPT_HOST` 환경변수만 주면 `nginx-proxy` + `acme-companion` 컨테이너가 알아서 리버스프록시 설정과 Let's Encrypt 인증서를 발급해주는 구조.
- Next.js standalone Dockerfile도 동일 계열(`WEBportfolio/portfolio/Dockerfile`)을 참고해 3-stage(deps → builder → runner) 빌드로 작성.

기존 nginx-proxy 컨테이너(`nginx-nginx-proxy-1`, `nginx-letsencrypt-1`)가 7일째 정상 구동 중이고 `proxy` 네트워크도 이미 존재함을 확인 후 그대로 활용(새로 안 만듦).

### 결정 — 서브도메인
기존 서비스들이 `iam.sanggyoon.com`, `investing.sanggyoon.com`처럼 `서비스명.sanggyoon.com` 패턴을 쓰고 있어서 동일 패턴을 유지하기로 하고, 사용자와 상의해 **`wanted.sanggyoon.com`**으로 확정.

### 만든 것
- `frontend/Dockerfile` — node:22-alpine 3-stage 빌드 (Next 16이 `engines.node >= 20.9.0`을 요구해서 여유 있게 22 LTS 선택)
- `frontend/.dockerignore` — node_modules, .next, .git, .env* 제외
- 루트 `docker-compose.yml` — `frontend` 서비스, `VIRTUAL_HOST`/`LETSENCRYPT_HOST`를 `.env`에서 주입, `proxy` 네트워크(external) 연결
- `.env` (커밋 안 됨, gitignore 처리됨) / `.env.example` (커밋됨) — `wanted.sanggyoon.com` 값

### 실행 및 검증
```bash
docker compose build     # 정상 빌드
docker compose up -d     # 컨테이너 기동
```
- nginx-proxy가 자동으로 `wanted.sanggyoon.com` vhost 설정을 생성한 것을 컨테이너 내부 `/etc/nginx/conf.d/default.conf`에서 확인
- `curl -H "Host: wanted.sanggyoon.com" http://localhost` → 200 (DNS 전엔 Host 헤더로 우회 테스트)

### DNS 설정 (사용자가 직접 진행)
서버 공인 IP(`49.174.150.122`) 확인 후, Gabia DNS 관리 페이지에서 `wanted` 호스트네임에 **CNAME → sanggyoon.com** 레코드 등록. (A 레코드가 아니라 CNAME으로 등록했는데, `sanggyoon.com` 자체가 이미 같은 IP를 가리키고 있어서 문제 없음 — `dig`로 `wanted.sanggyoon.com → sanggyoon.com → 49.174.150.122` 체인 확인)

### 문제 — 인증서 발급 확인
`docker exec nginx-letsencrypt-1 /app/force_renew`를 실행했더니 로그에 최초 한 번 `NXDOMAIN` 에러가 찍혀 있었음(DNS가 막 전파되던 시점에 조회해서 발생한 일시적 실패로 추정). 다시 확인해보니 `/etc/nginx/certs/wanted.sanggyoon.com/` 아래 인증서 파일들(fullchain.pem, key.pem 등)이 정상 생성돼 있었고, `curl -sI https://wanted.sanggyoon.com` → **HTTP/2 200**으로 최종 검증 완료.

### 커밋
`frontend/`, `Dockerfile`, `docker-compose.yml`, `.env.example`, ADR 버전 수정본을 하나의 커밋으로 묶어서 기록(`feat: scaffold Next.js frontend and self-host deploy config`).

## 3. CI/CD 구성 — GitHub Actions → GHCR → SSH 배포

### 목표
ADR §5대로 "PR엔 CI만, main 머지 시 GHCR 빌드+push+서버 배포"를 자동화하는 것.

### 문제 1 — GitHub Actions 러너가 서버에 어떻게 닿을 것인가
ADR §5는 "SSH로 서버 접속"이라고만 적혀 있었는데, 실제로 확인해보니 **라우터에 22번 포트가 열려있지 않았음**(80/443/25565만 포워딩됨). GitHub Actions는 클라우드에서 도는 러너라 공인 인터넷으로만 서버에 닿을 수 있는데, 두 가지 선택지가 있었음:
- A) 라우터에 22번(또는 비표준 포트) 포워딩을 새로 열기 — 간단하지만 SSH가 인터넷에 노출되어 brute-force 표면 증가
- B) GitHub Actions 러너를 매 실행마다 Tailscale tailnet에 임시로 조인시켜서, 포트를 전혀 열지 않고 tailnet 내부망으로만 SSH — 이 서버는 이미 Tailscale을 개인 인프라 접근 기본값으로 쓰고 있었음(SMB NAS, ComfyUI 등)

→ 사용자와 상의해 **B) Tailscale 경유**로 결정. 기존에 이 서버에서 유지해온 "개인용 서비스는 Tailscale 우선" 원칙과 일관된 선택.

### 준비 — 배포 전용 SSH 키페어
GitHub Actions가 서버에 로그인할 때 개인 SSH 키를 재사용하지 않고, 이 파이프라인 전용 키를 새로 발급:
```bash
ssh-keygen -t ed25519 -f ~/.ssh/gha_deploy_wantedhackathon -N "" -C "gha-deploy-wantedHackathon"
cat ~/.ssh/gha_deploy_wantedhackathon.pub >> ~/.ssh/authorized_keys
```
개인키는 GitHub Secrets(`SSH_PRIVATE_KEY`)에만 넣고, 공개키만 서버 `authorized_keys`에 등록.

### 만든 것 — 워크플로우 2개
- **`.github/workflows/ci.yml`**: `main`으로의 PR마다 `frontend`에서 `npm ci && npm run lint && npm run build`. 아직 백엔드(FastAPI)가 없어서 백엔드 CI 잡은 만들지 않음(있지도 않은 코드에 대한 빈 스텁을 미리 만들지 않기로 함).
- **`.github/workflows/deploy.yml`**: `main` push 시
  1. `build-and-push` job — Docker Buildx로 `frontend` 이미지 빌드 후 `ghcr.io/sanggyoon/wanted-frontend`에 `:latest`와 `:<short-sha>` 두 태그로 push (GHCR 로그인은 워크플로우 기본 `GITHUB_TOKEN`으로 처리, `docker/build-push-action` 사용)
  2. `deploy` job — `tailscale/github-action`으로 러너를 tailnet에 ephemeral node로 조인(`tag:ci`) → `appleboy/ssh-action`으로 서버의 Tailscale 호스트네임(`sanggyoonc5.tail5491a6.ts.net`)에 SSH 접속 → `IMAGE_TAG=<sha> docker compose pull && docker compose up -d`

### 문제 2 — docker-compose.yml이 build만 갖고 있어서 프로덕션 pull이 안 됨
로컬 개발/최초 배포 때는 `build: ./frontend`로 직접 빌드했지만, CD 파이프라인은 "GitHub에서 빌드해서 GHCR에 올린 이미지를 서버가 그냥 pull만 하는" 구조(ADR §5의 핵심 — 서버에 빌드 부담을 안 주는 것). 그래서 `docker-compose.yml`에 `image: ghcr.io/sanggyoon/wanted-frontend:${IMAGE_TAG:-latest}`를 `build`와 나란히 추가. Compose는 `build`와 `image`가 같이 있으면 `docker compose build`(로컬 개발용)와 `docker compose pull`(배포용)을 각각 다른 용도로 쓸 수 있게 해줘서, 파일 하나로 두 시나리오를 다 커버.

### 문제 3 — CR_PAT(Personal Access Token)이 필요하다고 안내했다가 정정
처음엔 ADR §5의 "CR_PAT" 문구를 그대로 따라가서 "GitHub Classic PAT을 `read:packages` 스코프로 발급해서 서버가 GHCR pull할 때 쓰자"고 안내했는데, 사용자가 GitHub UI에서 해당 메뉴를 못 찾음. 웹 검색으로 재조사한 결과:
- GitHub Classic PAT은 2026년 기준 아직 deprecated되지 않았고 메뉴 자체는 존재하지만(Settings → Developer settings → Personal access tokens → Tokens (classic)), 계정/시점에 따라 접근 경로가 다르게 보일 수 있음
- 더 근본적인 대안 발견: **워크플로우 실행 중에는 `GITHUB_TOKEN`으로도 GHCR private 이미지를 pull할 수 있음** (`packages: read` 권한만 job에 부여하면 됨). SSH 배포 스텝이 같은 워크플로우 run 안에서 실행되므로 `GITHUB_TOKEN`의 생명주기 안에 들어감.
→ **CR_PAT를 완전히 제거**하고 `deploy` job에 `permissions: packages: read` 추가, 스크립트에서 `secrets.GITHUB_TOKEN` + `github.actor`로 `docker login ghcr.io` 하도록 수정. 필요한 시크릿이 6개→5개로 줄어듦.

### 문제 4 — Tailscale 관리 콘솔 접속 에러 (`bad tailscale-authstate2 cookie`, 401)
로그인 리다이렉트 도중 쿠키 도메인이 어긋나서(`controlplane.tailscale.com` ↔ `login.tailscale.com` 간 쿠키 미스매치) 발생하는 알려진 문제. `https://login.tailscale.com/admin`으로 직접 접속하는 방식으로 우회 안내해서 해결.

### 문제 5 — "OAuth clients" 메뉴가 없다는 사용자 지적
처음 안내한 메뉴명("Settings → OAuth clients")이 최신 Tailscale 관리 콘솔과 달라서 사용자가 못 찾음. 웹 검색/공식 문서로 재조사해서 정확한 최신 경로를 확인:
1. **Access controls** 페이지에서 태그를 먼저 정의해야 함(ACL 정책 JSON에 `tagOwners`로 `tag:ci` 추가) — 태그가 없으면 OAuth client 생성 시 선택할 수 없음
2. 메뉴 이름이 **Settings → Trust credentials**로 바뀌어 있었음(예전엔 "OAuth clients"였음). **Credential** 버튼 → **OAuth** 선택 → 스코프 `auth_keys`를 **Write**로 설정(`tailscale/github-action`이 요구하는 스코프) → 태그로 `tag:ci` 선택 → 발급.

이 과정을 거쳐 `TS_OAUTH_CLIENT_ID`/`TS_OAUTH_CLIENT_SECRET` 발급 완료.

### GitHub Secrets 등록 (Repository secret으로)
Environment secret과의 차이(권한 승인 게이트가 필요한지 여부)를 설명하고, 지금 단계에선 승인 게이트가 필요 없으므로 **Repository secret**으로 등록하기로 결정. 최종 5개:
`SSH_HOST`, `SSH_USER`, `SSH_PRIVATE_KEY`, `TS_OAUTH_CLIENT_ID`, `TS_OAUTH_CLIENT_SECRET`

### 커밋
`.github/workflows/ci.yml`, `deploy.yml`, `docker-compose.yml` 수정분을 커밋(`feat: add CI/CD pipeline (GHCR build + Tailscale SSH deploy)`).

## 4. Push를 위한 Git 인증 설정

### 문제 — HTTPS push 인증 실패
지금까지 로컬 커밋만 쌓아뒀다가 첫 push를 시도하니 `fatal: could not read Username for 'https://github.com'` 에러. 이 서버엔 git credential helper도, GitHub용 SSH 키도 전혀 설정된 적이 없었음(레포를 `git clone`이 아니라 다른 방식으로 초기 세팅했던 것으로 추정).

### 해결 — 개인용 SSH 키 신규 발급
자동화 배포용 키(`gha_deploy_wantedhackathon`)와는 별개로, **사용자 본인이 이 서버에서 GitHub에 push할 때 쓸** 개인 키를 새로 생성:
```bash
ssh-keygen -t ed25519 -f ~/.ssh/id_ed25519 -N "" -C "sangreal4262@gmail.com"
```
공개키를 사용자에게 전달 → GitHub 본인 계정 Settings → SSH and GPG keys에 등록 → `ssh -T git@github.com`으로 인증 성공 확인 → `git remote set-url origin git@github.com:sanggyoon/202609_wantedHackathon.git`으로 HTTPS에서 SSH로 전환 → `git push origin main` 성공.

이 push로 방금 만든 CD 워크플로우가 처음으로 트리거됨.
