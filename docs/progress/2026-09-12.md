## 1. Supabase GitHub 연동으로 생긴 `supabase/migrations`의 정체 파악

Supabase ↔ GitHub 연동을 켜면서 `supabase/migrations/`가 생겼는데, 이게 무엇인지부터
정리했다. 흔히 아는 "데이터를 다른 플랫폼으로 옮기는" 마이그레이션이 아니라
**DB 스키마 변경 이력을 SQL 파일로 누적 관리하는 것**이다.

- 파일명 앞의 타임스탬프(`20260910124408_init.sql`)가 실행 순서다.
- Supabase는 원격 DB의 `supabase_migrations.schema_migrations` 테이블에 "어디까지
  적용했는지"를 기록해두고, **아직 적용 안 된 파일만** 순서대로 실행한다.
- 따라서 **한번 푸시한 마이그레이션 파일은 수정하면 안 된다.** 스키마를 바꾸려면
  새 파일을 추가한다.
- 원격은 앞으로만 쌓이고(데이터 보존), 로컬은 `supabase db reset`으로 0부터 재구축
  (데이터 소멸)한다. `--linked` 플래그를 붙이면 **원격을 날리므로** 습관적으로 쓰면 안 된다.

개념상으로는 IaC(Infrastructure as Code)의 하위 개념인 *database schema as code*에
해당한다. 단 Terraform 같은 선언형이 아니라 **명령형·누적형**이라, 파일 하나만 봐서는
현재 스키마를 알 수 없고 전체를 순서대로 재생해야 한다.

GitHub Actions와는 역할 층위가 다르다. Actions는 "언제 무엇을 실행할지"를 정하는
엔진이고(`ci.yml`은 lint/build만 담당, DB 얘기는 한 줄도 없음), 마이그레이션은
Supabase 서버가 읽어 실행하는 내용물이다. 둘은 서로를 모르는 별개 파이프라인이다.

## 3. 스키마 설계 확정 — `docs/Supabase_Schema_Design.md`

데이터 플로우 명세 v0.1이 "착수 전 확정 필요"로 남긴 8건 중, 스키마 모양을 바꾸는
항목을 결정했다.

| # | 결정 | 비고 |
| --- | --- | --- |
| D-1 | `expires_at`은 **최종 답변 시각 + 7일** | 생성 시 `created_at + 7일`로 초기화 후 답변 시 갱신 |
| D-2 | 만료 삭제는 **pg_cron**이 실행 | 백엔드 스케줄러 대신. ADR §10 방향과 일치 |
| D-3 | B 답변은 **1회만, 제출 즉시 읽기 전용** | DB 제약으로 강제 |
| D-4 | 링크 폐기 기능 **MVP 제외** | PRD §15 범위 밖 |
| D-5 | 원문 임시 저장 테이블 **없음** (서버 무저장) | |
| D-6 | 토큰은 **SHA-256 hex**, 만료 후에도 `cases` 행 유지 | 토큰 재사용 방지 |
| D-7 | DB 접근자는 **FastAPI 단독** | 브라우저는 Supabase에 직접 붙지 않음 |

**D-1에 함정이 있었다.** "최종 답변 기준"만 쓰면 B가 영영 답하지 않은 사건은 만료
시각이 존재하지 않아 영구히 남는다. 그래서 생성 시 `created_at + 7일`로 깔아두고
답변 시 갱신하는 2단계 구조가 됐다. 사건 총 수명 상한은 (B 대기 기간 + 7일)이고,
리포트가 존재하는 기간은 항상 7일이다.

### 테이블 구조

```
cases (D1)
 ├─ statement_cards   (D2)  UNIQUE(case_id, side)  — A/B 각 1장
 ├─ apologies         (D3)  PK = case_id           — 사건당 1장
 └─ mediation_reports (D4)  PK = case_id           — 사건당 1장
```

`apologies`와 `mediation_reports`는 **`case_id` 자체를 기본키로** 뒀다. 별도 제약 없이
"사건당 1건"이 DB 차원에서 강제되므로 D-3(1회 제출)이 앱 코드와 무관하게 보장된다.
`statement_cards`는 A·B 두 장이라 `UNIQUE(case_id, side)`로 같은 효과를 낸다.

PRD §11 초안에 없던 컬럼 둘을 추가했다 — `cases.answered_at`(D-1의 기준 시각),
`cases.purged_at`(삭제 완료를 검수로 증명하기 위한 증거).

### RLS

4개 테이블 모두 RLS를 켜되 **정책은 하나도 만들지 않는다.** RLS가 켜졌는데 정책이
없으면 모든 행이 거부되므로 `anon`·`authenticated` 키로는 아무것도 못 읽고,
`service_role`만 우회해서 통과한다. 프론트에 anon 키가 실수로 노출돼도 데이터가 새지
않는다.

"링크가 곧 권한"은 DB가 아니라 **FastAPI가 토큰 해시로 조회하는 계층**에서 구현한다.
RLS로 토큰을 검증하려면 요청마다 세션 변수를 세팅해야 해서 단일 접근자 구조에서는
복잡도만 늘어난다.

### 상태 전이 제약에 대한 방침

PK·UNIQUE 외에 상태 전이를 강제하는 CHECK 제약은 **일부러 두지 않았다.** 3주 일정에서
상태 머신이 아직 흔들릴 수 있고, 과도한 제약은 정당한 전이까지 막아 디버깅 비용을
키운다. 대신 조건부 UPDATE로 처리한다.

```sql
update cases
   set status = 'COUNTER_COMPLETED', answered_at = now(),
       expires_at = now() + interval '7 days'
 where id = $1 and status = 'COUNTER_DRAFT';
```

영향 행이 0이면 이미 전이된 것이므로 중복 제출로 간주한다. 결과물 테이블의 PK·UNIQUE가
최후의 방어선이다.

## 5. 마이그레이션 SQL 작성 — `supabase/migrations/` 2개

§3의 설계를 SQL로 옮겼다.

| 파일 | 내용 |
| --- | --- |
| `20260912113000_case_schema.sql` | 열거형 3개, 테이블 4개, 부분 인덱스, RLS |
| `20260912113100_expiry_purge.sql` | `purge_expired_cases()`, pg_cron 매시 스케줄 |

**파일을 2개로 나눈 이유**는 `pg_cron` 활성화가 Supabase에서 설치 스키마 제약으로
실패할 여지가 있어서다. 분리해두면 두 번째가 깨져도 핵심 스키마는 적용된 채로 남고,
대시보드 Database > Extensions에서 수동으로 켠 뒤 두 번째만 재시도하면 된다.

### 설계 스펙에서 벗어난 점

스펙 §4.3에 있던 `statement_cards(case_id)` 단독 인덱스를 **제거했다.**
`UNIQUE(case_id, side)`가 만드는 btree 인덱스의 선두 컬럼이 이미 `case_id`라
`where case_id = ?` 조회와 FK cascade 삭제를 모두 커버한다. 별도 인덱스는 쓰기 비용만
늘리는 중복이었다. 스펙에도 근거를 적어 반영했다.

### 구현 시 붙인 안전장치

- `purge_expired_cases()`를 `security definer` + `set search_path = public, pg_temp`로
  고정 — cron 잡 실행 주체와 무관하게 동일 권한으로 동작시키고 탐색 경로 하이재킹을 막는다.
  함수의 기본 `PUBLIC` 실행 권한은 회수했다.
- 스케줄 등록 앞에 `cron.unschedule` 가드 — Preview Branch 재생성 등으로 재실행돼도
  잡이 중복 등록되지 않는다.
- `gen_random_uuid()`는 PG13+ 코어(`pg_catalog`) 내장 함수다. `init.sql`이 `pgcrypto`를
  `extensions` 스키마에 설치했지만 search_path와 무관하게 동작한다 (`config.toml`상 PG17).

### 검증 상태 — 미검증

**이 SQL은 아직 한 번도 실행되지 않았다.** 로컬에 Postgres도 `psql`도 없고 Docker 데몬도
꺼져 있어 문법 검사를 못 했다. PR의 Supabase Preview Branch에서 처음 실행된다.

순정 `postgres:17` 컨테이너로 미리 돌려보는 안도 검토했으나, 정작 가장 불확실한
`pg_cron`이 순정 이미지에 없어 검증 범위 밖이라 실익이 적다고 판단하고 PR로 직행했다.
