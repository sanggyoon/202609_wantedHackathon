## 1. 첫 CD 실행 결과 확인 — 3회 모두 실패 → 원인 특정 → 수정 완료

GitHub Actions API로 확인한 결과 CD(`deploy.yml`)가 3번(`63a3a67`, `c4fc180`, `579b983`) 모두
`deploy` job에서 실패. `build-and-push` job은 매번 성공(GHCR에 이미지는 정상 push됨).

`deploy` job 중 실패 지점은 "Deploy over SSH (via Tailscale)" 스텝. GitHub API로 로그 원문을
받으려 했으나 `Must have admin rights to Repository.`(403) — 세션에 GitHub 인증 토큰이 없어
실패. 대신 서버 쪽 `journalctl -u ssh`로 교차 확인한 결과, 세 번의 CD 실행 시각과 정확히
일치하는 시점에 `Connection closed by authenticating user sanggyoon ... [preauth]` 로그가
찍혀 있었음 — Tailscale ephemeral 러너가 서버까지 도달은 했지만 pubkey 인증 시도 자체가
없이 연결이 끊기는 패턴. `~/.ssh/authorized_keys`의 키는 정상이라 서버 쪽 문제는 아니라고
잠정 판단(→ GitHub Secrets 쪽 문제로 추정).

사용자가 Actions 웹 UI에서 실제 에러 메시지를 확인해 공유: `ssh.ParsePrivateKey: ssh: no key
found`. **확정 원인 — `SSH_PRIVATE_KEY` 시크릿에 `-----BEGIN OPENSSH PRIVATE KEY-----` /
`-----END OPENSSH PRIVATE KEY-----` 마커 라인을 포함하지 않고 등록**했던 것. 사용자가 마커를
포함해 시크릿을 다시 등록 → 재실행(Re-run) → **success** 확인.

(참고: 같은 근본 원인을 진단 중, 향후 유사 문제를 원천 차단하기 위해 base64 인코딩 방식으로
`deploy.yml`을 바꾸는 시도를 했었으나, 원본 방식이 이미 정상 동작 확인됐으므로 되돌리고
`SSH_PRIVATE_KEY` 원본 방식을 유지하기로 함 — 불필요한 시크릿 추가를 피함.)

**검증.** GitHub API로 `579b983` 실행이 `success`로 전환된 것 확인. 서버의 frontend 컨테이너가

## 2. 백엔드(FastAPI) 스캐폴딩

ADR §2 결정(Python + FastAPI, async, Pydantic 검증, 자동 `/docs`)에 따라 `backend/`를 새로 만듦.

### 준비 — Python 패키지 매니저 부재
서버에 `pip`/`ensurepip`/`uv` 모두 없었음(`python3 -m pip` → `No module named pip`, apt로 설치하려면
sudo 필요). Node 때(nvm)와 같은 방식으로, 팀원 로컬 개발에도 재사용 가능하도록 **uv를 사용자
홈(`~/.local/bin`)에 설치**해 sudo 없이 해결.
```bash
curl -LsSf https://astral.sh/uv/install.sh | sh
```

### 구조
```
backend/
  pyproject.toml   # fastapi, uvicorn[standard], pydantic-settings + dev: ruff
  app/
    main.py        # FastAPI() 인스턴스, CORS, health 라우터 등록
    core/config.py # pydantic-settings 기반 Settings
    api/health.py  # GET /health (async, Pydantic response_model)
  Dockerfile        # ghcr.io/astral-sh/uv 빌더 → python:3.12-slim-bookworm 런타임, 3-stage 아님(uv 특성상 2-stage)
  .dockerignore
  .gitignore        # .venv/, __pycache__/ 등 (uv init이 자동 생성 안 해줘서 직접 추가)
```
`uv init --app`이 기본으로 `src/` 레이아웃 + `build-system`(패키지 배포용)을 만들어줬는데, 이 프로젝트는
배포 가능한 라이브러리가 아니라 서비스라서 불필요 → `[tool.uv] package = false`로 바꾸고
`app/`을 루트에 평평하게 둠.

### 검증
- `uv sync` → 정상 설치(Python 3.12.14 다운로드까지 자동)
- `uv run uvicorn app.main:app` → `GET /health` `{"status":"ok"}`, `GET /docs` 200, `openapi.json`의
  `info.title` 정상 확인
- `uv run ruff check .` → 통과
- `docker build` → 정상 빌드, 컨테이너 기동 후 `/health` 정상 응답 확인(로컬 테스트용 이미지는 빌드 후 삭제)

## 3. 백엔드 CI 잡 추가

ADR §5에 명시된 "backend: ruff lint + import 검증"을 `.github/workflows/ci.yml`에 추가:
```yaml
  backend:
    runs-on: ubuntu-latest
    defaults:
      run:
        working-directory: backend
    steps:
      - uses: actions/checkout@v4
      - uses: astral-sh/setup-uv@v10
        with:
          enable-cache: true
          cache-dependency-glob: backend/uv.lock
      - run: uv sync --locked
      - run: uv run ruff check .
      - run: uv run python -c "import app.main"
```
프론트엔드 잡과 마찬가지로 path filter 없이 모든 PR에서 실행(레포가 작아 굳이 나눌 필요 없음).

## 4. DB 세팅 — 결정 번복: 자체 Postgres → Supabase Cloud

작업을 시작하려고 서버의 기존 Postgres를 확인하니, ADR이 가정한 "평범한 Postgres 컨테이너"가
아니라 **자체 호스팅 Supabase 스택**(`supabase-db`, `supabase-rest`, `supabase-meta` 컨테이너)이었음.
사용자에게 확인한 결과, **이 컨테이너는 이 해커톤 프로젝트와 무관한 별도 서비스**였고, 애초에
DB 관련 결정 자체가 바뀌어 있었음(문서에는 반영 안 된 상태):

- 최초엔 "3주 이후에도 계속 유지"를 전제로 자체 서버 Postgres를 쓰기로 했었으나, 서비스를
  계속 유지하려면 LLM API 비용 또는 로컬 LLM GPU 리소스 부담이 생기는데 그걸 계속 짊어질
  계획이 없어 **프로젝트를 해커톤 기간(3주)만 운영하고 종료**하기로 결정 변경.
- 종료 시 데이터는 백업만 하고 인프라는 폐기할 것이므로, 자체 서버에 새 DB/유저를 만드는 것보다
  **Supabase Cloud**(관리형)를 썼다가 프로젝트째 삭제하는 쪽이 총비용이 낮음.

→ `docs/Tech_ADR.md` §6을 이 내용으로 갱신(이전 결정은 `<details>`로 보존해 왜 바뀌었는지 추적
가능하게 함), CI/CD 다이어그램의 `host Postgres(mediation)`도 `Supabase Cloud(관리형 Postgres)`로
수정.

**Supabase 프로젝트는 아직 미생성.** 이 세션에 `claude.ai Supabase` MCP 연동이 붙어 있는 것을
확인했으나 인증이 안 된 상태 — Claude Code에서 `/mcp` 명령으로 "claude.ai Supabase"를 선택해
인증해야 다음 세션에서 프로젝트 생성으로 진행 가능.

## 5. 백엔드를 docker-compose / CD 파이프라인에 편입

ADR 다이어그램(`Nginx(443) ─ /api → backend:8000`)대로 프론트와 같은 도메인
아래 **경로 기반 라우팅**으로 백엔드를 붙였다.

### 조사 — nginx-proxy가 경로 기반 라우팅을 지원하는가
현재 떠 있는 이미지가 `nginxproxy/nginx-proxy`(커뮤니티 포크)임을 확인. 이 이미지의
템플릿(`/app/nginx.tmpl`)에 `VIRTUAL_PATH` 처리 로직이 있어 **같은 `VIRTUAL_HOST` 아래
여러 컨테이너를 경로별로 분기**시킬 수 있음을 확인 → 서브도메인을 새로 만들 필요 없이
`wanted.sanggyoon.com/api/*`만 backend로 보내면 됨.

### 코드 변경 — `/api` 프리픽스
`VIRTUAL_PATH=/api/`는 경로를 벗기지 않고(strip 안 함) 그대로 백엔드로 전달하므로,
FastAPI 쪽 라우트도 `/api`를 포함하도록 맞춤:
```python
app = FastAPI(docs_url="/api/docs", openapi_url="/api/openapi.json")
app.include_router(health_router, prefix="/api")
```
(`docs_url`/`openapi_url`도 안 바꾸면 `/docs`가 `/api/openapi.json`을 못 찾아 Swagger UI가
깨짐 — 함께 프리픽스를 맞춰줌.)

### `docker-compose.yml`에 `backend` 서비스 추가
`frontend`와 동일 패턴 + `VIRTUAL_PATH` 한 줄만 추가:
```yaml
  backend:
    build: ./backend
    image: ghcr.io/sanggyoon/wanted-backend:${IMAGE_TAG:-latest}
    environment:
      - VIRTUAL_HOST=${VIRTUAL_HOST}
      - VIRTUAL_PATH=/api/
      - LETSENCRYPT_HOST=${LETSENCRYPT_HOST}
    restart: always
    networks:
      - proxy
```
`VIRTUAL_PORT`는 안 줬는데도 정상 동작 — nginx-proxy가 `Dockerfile`의 `EXPOSE 8000`을
자동 인식(frontend도 같은 방식으로 `EXPOSE 3000`만으로 동작 중이던 것과 동일).

### `deploy.yml` — frontend 하나만 빌드하던 걸 matrix로 확장
```yaml
    strategy:
      matrix:
        service: [frontend, backend]
```
로 바꿔 두 이미지(`wanted-frontend`, `wanted-backend`)를 같은 short-sha 태그로 함께
build & push하고, `deploy` job의 스크립트도 `docker compose pull frontend` /
`up -d frontend`처럼 서비스명을 박아두던 걸 인자 없는 `docker compose pull` /
`up -d`로 바꿔 컴포즈 파일에 있는 서비스 전부(현재 frontend+backend)를 배포하도록 함.

### 검증 — 실제 프로덕션에 반영해서 확인
로컬 빌드(`docker compose build backend`) 후 서버에서 바로 `docker compose up -d`까지
실행(이 서버가 곧 운영 서버라 별도 스테이징이 없음):
- `docker ps` → `backend` 컨테이너 정상 기동, 로그에 `Uvicorn running on http://0.0.0.0:8000`
- `curl https://wanted.sanggyoon.com/api/health` → `{"status":"ok"}`
- `curl -o /dev/null -w "%{http_code}" https://wanted.sanggyoon.com/api/docs` → `200`
- `curl -o /dev/null -w "%{http_code}" https://wanted.sanggyoon.com/` → `200` (frontend 회귀 없음)
- nginx-proxy 컨테이너 내부 `/etc/nginx/conf.d/default.conf`에서 `location /api/ { proxy_pass ...backend... }` 블록이 자동 생성된 것 확인
- `docker compose config` / `python3 -c "yaml.safe_load(...)"`로 세 파일(`ci.yml`, `deploy.yml`, `docker-compose.yml`) 문법 검증
