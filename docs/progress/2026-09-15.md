## 1. 결정 — DB 기준으로 통일

API·프론트·DB가 같은 고소장 카드를 서로 다른 필드로 표현하던 문제(09-14 §3)를
**DB `statement_cards`·`apologies` 컬럼명 기준으로** 통일했다.

| 새 이름 (= DB 컬럼) | 이전 | 비고 |
| --- | --- | --- |
| `incident_description` | `incident` | |
| `emotions` | — | **유실되던 것을 복구** |
| `emotion_reason` | `feeling`의 일부 | |
| `hurt_point` | `feeling`의 일부 | 컬럼 추가 |
| `desired_outcome` | `wish` | |
| `expected_behavior` | `expectation` | 컬럼 추가 |
| `assumption` | `guess` | 컬럼 추가 |
| `cute_charge`·`incident_summary`·`different_viewpoint` | — | 생성 주체 없음 → 항상 빈 값 |

사과문도 함께 맞췄다 — `understood`→`understood_point`, `promise`→`future_commitment`,
`admitted`→`admitted_point`(컬럼 추가).

**alias를 두지 않아 요청·응답 모두 snake_case다.** DB 컬럼명이 그대로 API 필드명이자
프론트 타입 필드명이 된다. 프론트에는 이미 선례가 있었다 — `lib/api/mediation.ts`가
`common_ground`·`hurt_points_a` 같은 snake_case를 쓰고 있었다.

## 2. 착수 후 컬럼이 하나 늘었다 — `hurt_point`

09-14에 계획한 컬럼은 넷이었는데 다섯이 됐다. 프론트가 감정 칸 하나에 셋을 합쳐 넣고
있던 것을 작업 중에 발견했다.

```js
feeling = [hurtPoint, emotions.join(", "), emotion.reason].join("\n")
```

DB에 `hurt_point`가 없으면 그대로 버려진다. `expectation`·`guess`와 정확히 같은
성격(프론트에 있는데 DB에 없음)이라 승인된 원칙대로 함께 흡수했다.

## 3. 덤으로 고쳐진 버그 — 감정 목록 유실

대화 엔진(`ComplaintConversationState.emotion`)은 감정을 `["걱정","서운함"]` 목록으로
뽑는다. 그런데 카드로 옮기는 단계에서 한 덩어리 문자열로 합쳐지며 **목록이 통째로
버려지고 있었다.** 구조를 그대로 옮기니 해소됐다.

중재 리포트도 개선됐다. `mediation.stated_feelings()`가 `emotions[]`를 우선 사용하고,
비어 있으면 `emotion_reason`으로 대체하며, 미공유(`"공유하지 않은 내용"`)는 `[]`로
처리한다 — **미공유를 감정으로 둔갑시키지 않는다.**

## 4. 화면 토글과 DB 필드는 1:1이 아니다

공유 항목 선택 화면(`ShareSelectScreen`)의 "그때 느낀 감정" 토글 **하나**가
`emotions`·`emotion_reason`·`hurt_point` **셋**을 함께 덮는다. 사용자에게는 여전히
한 항목으로 보이고 UX는 그대로다.

표시용으로 셋을 합칠 때는 `types.ts`의 `feelingText()`를 쓴다. 이것은 화면 표시용이며
저장 형태가 아니다.

`PreviewScreen`에는 감정 목록 편집을 쉼표 구분 textarea로 추가했다. 기존에는 `feeling`
한 덩어리를 편집했는데, 목록이 분리되면서 편집 수단이 필요해졌다.

## 6. Supabase Cloud 적용

백필 불필요.

```sql

alter table statement_cards add column expected_behavior text;
alter table statement_cards add column assumption        text;

`supabase db push`로 적용했고 `supabase migration list`로 로컬·원격 버전 일치를 확인했다.

```
✅ 20260910124408   ✅ 20260912113000   ✅ 20260912113100   ✅ 20260915101500

`supabase db dump`로 컬럼을 직접 확인하려 했으나 Docker 데몬이 꺼져 있어 실패했다
(`db dump`는 컨테이너에서 `pg_dump`를 돌린다). 마이그레이션은 트랜잭션으로 적용되므로
이력에 기록됐다는 것은 다섯 컬럼이 모두 들어갔다는 뜻이다. 직접 확인이 필요하면
SQL Editor에서 `\d statement_cards`를 보면 된다.

## 7. 로컬 개발 환경 — `uv` 설치

백엔드 테스트를 돌리려는데 로컬에 `uv`가 없었다(`python3`는 3.9라 프로젝트의 3.12 문법을
해석하지 못한다). CI가 쓰는 것과 같은 도구이므로 `brew install uv`로 설치했다.

테스트 실행에 함정이 하나 있다. `tests/`에 `__init__.py`가 없어 일반적인 discover가
실패한다.

```bash
cd backend
PYTHONPATH=.:tests uv run python -m unittest test_respondent_flow
```

`PYTHONPATH`에 `tests`를 함께 넣어야 한다. CI는 테스트를 돌리지 않으므로(lint·import
검증만) 이 문제가 드러나지 않고 있었다.

## 8. 사건 계층 착수 — DB 접근과 링크 발급

카드 형태가 세 곳에서 일치하게 되면서 저장 계층을 붙일 수 있게 됐다.

### 8.1 DB 접근 계층 — `psycopg` 3

`supabase-py`(PostgREST) 대신 `psycopg`를 골랐다. 기존 라우트가 동기(`def`)라 async/sync가
섞이지 않고, 앞으로 필요한 **조건부 UPDATE의 영향 행 수**와 **카드+리포트+전이를 한
트랜잭션**을 생 SQL로 쓰기 편하다.

두 가지를 조심해야 했다.

**풀은 최초 사용 시점에 만든다.** import 시점에 연결하면 `DATABASE_URL`이 없는 환경에서
앱이 뜨지 않는다. CI가 `python -c "import app.main"`으로 임포트를 검증하므로 지연 생성이
필수다.

**prepared statement를 끈다.** Supabase Transaction pooler(PgBouncer)는 prepared statement를
세션 간에 유지하지 못한다. `prepare_threshold=None`을 주지 않으면 간헐적으로 실패한다.

### 8.2 엔드포인트 둘

| Method | Path | 하는 일 |
| --- | --- | --- |
| `POST` | `/api/cases` | 사건 생성, 토큰 2개 발급 |
| `GET` | `/api/cases/{token}` | 상태·역할·가능한 행동·내용 |

`POST`는 **토큰 원문이 노출되는 유일한 응답**이다. 서버는 SHA-256 해시만 저장하므로 이후
어떤 조회로도 다시 얻을 수 없다.

`GET`의 `X-Writer-Token`은 선택이다. 유효하면 `viewer_role: "A"`, 없거나 불일치하면 `"B"`다.
**불일치를 오류로 처리하지 않는다** — B는 애초에 이 토큰이 없고, 토큰 없는 접근이 정상
경로다. 이걸 403으로 만들면 B가 링크를 열 수 없다.

`available_actions`는 서버가 계산해 내려준다(API_Design A-5). 상태 전이 규칙이 프론트·백에
이중으로 흩어지는 것을 막는다.

### 8.3 만료 lazy 검사를 같이 넣었다

`GET`은 조회 직후 `expires_at <= now()`를 확인하고 지났으면 410을 반환한다. `status`가
이미 `EXPIRED`인 경우도 같다. 어느 쪽이든 `content`를 담지 않는다.

**나중에 붙이면 안 되는 이유**가 있다. `pg_cron` 배치는 최대 1시간 지연되므로 이 검사가
없으면 그 사이 만료된 사건의 내용이 그대로 나간다. 그리고 조회 경로가 늘어난 뒤에 붙이면
전부 다시 훑어야 한다.

### 8.4 오류 형식 결정 — `{detail}` 유지

미결이던 항목을 정했다. 기계가 분기해야 하는 구분은 **HTTP 상태 코드가 이미 제공한다**
(404 vs 410 vs 409). 별도 `code` 필드를 두면 같은 정보를 두 곳에 적는 셈이고 기존 두
엔드포인트까지 고쳐야 한다. `detail`은 사람이 읽는 문구만 담는다.

`DATABASE_URL` 미설정은 503으로 처리하되 **원인을 응답에 담지 않는다.**

### 8.5 테스트 18개 추가, CI에 연결

목으로 저장소 계층을 막고 API 동작을 검증한다. 눈에 띄는 것 몇 가지.

- 저장소에 **해시만** 넘어가는지 (원문이 넘어가면 DB에 원문이 남는다)
- 잘못된 writer 토큰이 **오류가 아닌지**
- 만료 응답에 `content`가 없는지
- 503 응답에 `DATABASE_URL`이라는 단어가 없는지

**`ci.yml`에 테스트 실행을 추가했다.** 그전까지 CI는 `ruff check`와 `import app.main`만
돌려서 **테스트가 깨져도 통과했다.** 실행에 함정이 있어 주석으로 남겼다 — `tests/`에
`__init__.py`가 없어 `-t tests`로 top-level을 옮기고 `PYTHONPATH`에 `tests`를 함께 넣어야
한다.

### 8.6 실DB 검증에서 버그를 하나 잡았다

테스트 18개는 저장소 계층을 목으로 막으므로 **SQL 자체는 한 번도 돌지 않은 상태였다.**
로컬 `postgres:17` 컨테이너에 마이그레이션 4개를 적용해 운영과 같은 구조를 만들고,
목 없이 리포지토리와 API를 실행했다.

**목으로는 잡히지 않던 버그가 나왔다.**

```
cards.A.expected_behavior
  Input should be a valid string, input_value=None
```

`hurt_point`·`expected_behavior`·`assumption` 컬럼은 nullable이라 저장된 카드를 읽으면
`None`이 온다. 그런데 `SharedStatement`는 이들을 `str`(non-nullable)로 받는다. 즉
**카드가 저장된 사건을 조회하면 500이 났다.** 사건 계층이 붙는 순간 바로 터질 자리였다.

`SharedStatement`에 `mode="before"` 검증기를 붙여 `None`을 빈 문자열로 받게 고쳤다.
"값 없음"을 빈 문자열 하나로 통일해 프론트가 분기를 두 벌 두지 않게 한다.
`different_viewpoint`만은 `null`을 유지한다 — "아직 생성되지 않음"과 "빈 값"이 다르다.

회귀 테스트를 추가하고, **검증기를 임시로 빼서 그 테스트가 실제로 실패하는지 확인**했다.
통과만 보고 넘어가면 아무것도 검증하지 않는 테스트를 남길 수 있다.
