## 1. 결정 — DB 기준으로 통일

API·프론트·DB가 같은 고소장 카드를 서로 다른 필드로 표현하던 문제(09-14 §3)를
**DB `statement_cards`·`apologies` 컬럼명 기준으로** 통일했다.

| 새 이름 (= DB 컬럼) | 이전 | 비고 |
| --- | --- | --- |
| `incident_description` | `incident` | |
| `emotions` | — | **유실되던 것을 복구** |
| `emotion_reason` | `feeling`의 일부 | |
| `hurt_point` | `feeling`의 일부 | 컬럼 추가 |
| `desired_outcome` | `wish` | |
| `expected_behavior` | `expectation` | 컬럼 추가 |
| `assumption` | `guess` | 컬럼 추가 |
| `cute_charge`·`incident_summary`·`different_viewpoint` | — | 생성 주체 없음 → 항상 빈 값 |

사과문도 함께 맞췄다 — `understood`→`understood_point`, `promise`→`future_commitment`,
`admitted`→`admitted_point`(컬럼 추가).

**alias를 두지 않아 요청·응답 모두 snake_case다.** DB 컬럼명이 그대로 API 필드명이자
프론트 타입 필드명이 된다. 프론트에는 이미 선례가 있었다 — `lib/api/mediation.ts`가
`common_ground`·`hurt_points_a` 같은 snake_case를 쓰고 있었다.

## 2. 착수 후 컬럼이 하나 늘었다 — `hurt_point`

09-14에 계획한 컬럼은 넷이었는데 다섯이 됐다. 프론트가 감정 칸 하나에 셋을 합쳐 넣고
있던 것을 작업 중에 발견했다.

```js
feeling = [hurtPoint, emotions.join(", "), emotion.reason].join("\n")
```

DB에 `hurt_point`가 없으면 그대로 버려진다. `expectation`·`guess`와 정확히 같은
성격(프론트에 있는데 DB에 없음)이라 승인된 원칙대로 함께 흡수했다.

## 3. 덤으로 고쳐진 버그 — 감정 목록 유실

대화 엔진(`ComplaintConversationState.emotion`)은 감정을 `["걱정","서운함"]` 목록으로
뽑는다. 그런데 카드로 옮기는 단계에서 한 덩어리 문자열로 합쳐지며 **목록이 통째로
버려지고 있었다.** 구조를 그대로 옮기니 해소됐다.

중재 리포트도 개선됐다. `mediation.stated_feelings()`가 `emotions[]`를 우선 사용하고,
비어 있으면 `emotion_reason`으로 대체하며, 미공유(`"공유하지 않은 내용"`)는 `[]`로
처리한다 — **미공유를 감정으로 둔갑시키지 않는다.**

## 4. 화면 토글과 DB 필드는 1:1이 아니다

공유 항목 선택 화면(`ShareSelectScreen`)의 "그때 느낀 감정" 토글 **하나**가
`emotions`·`emotion_reason`·`hurt_point` **셋**을 함께 덮는다. 사용자에게는 여전히
한 항목으로 보이고 UX는 그대로다.

표시용으로 셋을 합칠 때는 `types.ts`의 `feelingText()`를 쓴다. 이것은 화면 표시용이며
저장 형태가 아니다.

`PreviewScreen`에는 감정 목록 편집을 쉼표 구분 textarea로 추가했다. 기존에는 `feeling`
한 덩어리를 편집했는데, 목록이 분리되면서 편집 수단이 필요해졌다.

## 6. Supabase Cloud 적용

`supabase/migrations/20260915101500_align_api_schema.sql` — 컬럼 5개, 전부 nullable,
백필 불필요.

```sql
alter table cases           add column writer_token_hash text;
alter table statement_cards add column hurt_point        text;
alter table statement_cards add column expected_behavior text;
alter table statement_cards add column assumption        text;
alter table apologies       add column admitted_point    text;
```

`supabase db push`로 적용했고 `supabase migration list`로 로컬·원격 버전 일치를 확인했다.

```
✅ 20260910124408   ✅ 20260912113000   ✅ 20260912113100   ✅ 20260915101500
```

`supabase db dump`로 컬럼을 직접 확인하려 했으나 Docker 데몬이 꺼져 있어 실패했다
(`db dump`는 컨테이너에서 `pg_dump`를 돌린다). 마이그레이션은 트랜잭션으로 적용되므로
이력에 기록됐다는 것은 다섯 컬럼이 모두 들어갔다는 뜻이다. 직접 확인이 필요하면
SQL Editor에서 `\d statement_cards`를 보면 된다.

## 7. 로컬 개발 환경 — `uv` 설치

백엔드 테스트를 돌리려는데 로컬에 `uv`가 없었다(`python3`는 3.9라 프로젝트의 3.12 문법을
해석하지 못한다). CI가 쓰는 것과 같은 도구이므로 `brew install uv`로 설치했다.

테스트 실행에 함정이 하나 있다. `tests/`에 `__init__.py`가 없어 일반적인 discover가
실패한다.

```bash
cd backend
PYTHONPATH=.:tests uv run python -m unittest test_respondent_flow
```

`PYTHONPATH`에 `tests`를 함께 넣어야 한다. CI는 테스트를 돌리지 않으므로(lint·import
검증만) 이 문제가 드러나지 않고 있었다.
