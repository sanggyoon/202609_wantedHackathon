# 2026-09-16 진행상황

사건 저장 기능 네 개를 구현했다. **제품이 처음으로 사건 생성부터 최종 답변까지 끝까지
동작한다.**

작업 브랜치: `feat/case-writes`

---

## 1. 어제까지와 달라진 것

어제는 링크를 만들고 열 수는 있었지만 **내용을 저장할 수 없었다.** AI가 고소장을
만들어줘도 어디에도 남지 않고 날아갔다.

```
POST /api/cases/{token}/statement       A 고소장 확정 / B 맞고소 제출
POST /api/cases/{token}/response-type   B의 사과·맞고소 선택
POST /api/cases/{token}/apology         B 사과문 제출
```

이 셋이 붙으면서 `DRAFT → AWAITING_RESPONSE → *_DRAFT → *_COMPLETED` 전이가 전부
연결됐다.

## 2. 동시 제출 방어를 DB에 맡겼다

모든 쓰기는 **상태 조건부 UPDATE를 먼저** 실행한다.

```sql
update cases set status = 'AWAITING_RESPONSE'
 where id = %s and status = 'DRAFT';
```

이 UPDATE가 사건 행에 락을 걸기 때문에, 동시에 들어온 두 번째 요청은 첫 번째가 커밋될
때까지 기다렸다가 **바뀐 상태를 보고 0행을 얻는다.** 애플리케이션이 따로 잠금을 관리하지
않아도 DB가 직렬화한다. 영향 행이 0이면 409다.

스레드 8개로 실제 동시 제출을 던져봤다.

| 대상 | 200 | 409 | 저장된 행 |
| --- | --- | --- | --- |
| A 고소장 | 1 | 7 | 카드 1장 |
| 응답 방식 선택 | 1 | 7 | — |
| 사과문 | 1 | 7 | 사과문 1장 |

응답 방식은 `COUNTER`와 `APOLOGY`를 섞어 던졌는데도 최종 상태가 한쪽으로만 정해졌다.

## 3. B의 맞고소는 한 트랜잭션

B 카드 저장·중재 리포트 저장·상태 전이가 한 트랜잭션이다. 어느 하나가 실패하면 전부
롤백되므로 사용자는 온전히 재시도할 수 있다.

**리포트 생성(LLM 호출)은 트랜잭션 밖에서 먼저 한다.** 생성이 실패하면 B 카드도 저장되지
않아 502를 받고 다시 제출하면 된다. 반대 순서였다면 카드만 남고 리포트가 없는 사건이
생긴다.

리포트 생성 실패 시 **provider 예외를 노출하지 않는다.** 테스트로 확인했다 — 502 응답에
`openai down` 같은 문구가 섞이지 않는다.

## 4. 쓰기 경로도 만료를 막는다

조회만 막으면 충분하지 않다. 만료된 사건에 답변을 제출할 수 있으면 `pg_cron`이 지운 뒤에
새 데이터가 들어와 되살아난다. `_active()` 헬퍼가 조회와 쓰기 양쪽에서 같은 검사를 한다.

## 5. 권한 — A만 요구하고 B는 요구하지 않는다

| 엔드포인트 | `X-Writer-Token` |
| --- | --- |
| `statement` (side A) | **필수.** 없으면 403 |
| `statement` (side B) | 불필요 |
| `response-type` | 불필요 |
| `apology` | 불필요 |

B에게 토큰을 요구하면 "링크 하나로 전달이 끝난다"는 구조가 깨진다. B의 중복 제출은 토큰이
아니라 §2의 조건부 UPDATE와 DB 제약이 막는다.

## 6. 테스트가 잡은 것 — 공백만 있는 사과문

`Field(min_length=1)`로는 `"   "`가 통과한다. 프론트는 `!value.body.trim()`으로 막고 있었는데
서버는 안 막고 있었다. `StringConstraints(strip_whitespace=True, min_length=1)`로 고쳤다.

프론트만 막고 서버가 안 막으면 API를 직접 호출하는 경로에서 빈 사과문이 저장된다.

## 7. 검증

| 항목 | 결과 |
| --- | --- |
| `ruff check` | 통과 |
| `unittest` 72개 | 통과 |
| 실DB 전체 흐름 14단계 | 통과 |
| 실DB 동시 제출 (스레드 8개 × 3종) | 통과 |

실DB 검증은 `postgres:17` 컨테이너에 마이그레이션 4개를 적용해 운영과 같은 구조를 만들고
목 없이 돌렸다. 확인한 것 중 목으로는 잡히지 않는 것들:

- 맞고소 완료 시 `expires_at`이 **`answered_at` 기준 +7일**로 갱신되는가
- 중재 리포트의 `hurt_points_a/b`가 각 측 `emotions[]`를 그대로 담는가
- 사과 경로에는 중재 리포트가 **생기지 않는가**
- 잘못된 순서(A 제출 전 응답 선택, `DRAFT`에서 사과문)가 409인가
- 만료 후 **쓰기**가 410인가
