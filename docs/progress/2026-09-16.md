# 2026-09-16 진행상황

사건 저장 기능 네 개를 구현했다. **제품이 처음으로 사건 생성부터 최종 답변까지 끝까지
동작한다.**

작업 브랜치: `feat/case-writes`

---

## 1. 어제까지와 달라진 것

어제는 링크를 만들고 열 수는 있었지만 **내용을 저장할 수 없었다.** AI가 고소장을
만들어줘도 어디에도 남지 않고 날아갔다.

```
POST /api/cases/{token}/statement       A 고소장 확정 / B 맞고소 제출
POST /api/cases/{token}/response-type   B의 사과·맞고소 선택
POST /api/cases/{token}/apology         B 사과문 제출
```

이 셋이 붙으면서 `DRAFT → AWAITING_RESPONSE → *_DRAFT → *_COMPLETED` 전이가 전부
연결됐다.

## 2. 동시 제출 방어를 DB에 맡겼다

모든 쓰기는 **상태 조건부 UPDATE를 먼저** 실행한다.

```sql
update cases set status = 'AWAITING_RESPONSE'
 where id = %s and status = 'DRAFT';
```

이 UPDATE가 사건 행에 락을 걸기 때문에, 동시에 들어온 두 번째 요청은 첫 번째가 커밋될
때까지 기다렸다가 **바뀐 상태를 보고 0행을 얻는다.** 애플리케이션이 따로 잠금을 관리하지
않아도 DB가 직렬화한다. 영향 행이 0이면 409다.

스레드 8개로 실제 동시 제출을 던져봤다.

| 대상 | 200 | 409 | 저장된 행 |
| --- | --- | --- | --- |
| A 고소장 | 1 | 7 | 카드 1장 |
| 응답 방식 선택 | 1 | 7 | — |
| 사과문 | 1 | 7 | 사과문 1장 |

응답 방식은 `COUNTER`와 `APOLOGY`를 섞어 던졌는데도 최종 상태가 한쪽으로만 정해졌다.

## 3. B의 맞고소는 한 트랜잭션

B 카드 저장·중재 리포트 저장·상태 전이가 한 트랜잭션이다. 어느 하나가 실패하면 전부
롤백되므로 사용자는 온전히 재시도할 수 있다.

**리포트 생성(LLM 호출)은 트랜잭션 밖에서 먼저 한다.** 생성이 실패하면 B 카드도 저장되지
않아 502를 받고 다시 제출하면 된다. 반대 순서였다면 카드만 남고 리포트가 없는 사건이
생긴다.

리포트 생성 실패 시 **provider 예외를 노출하지 않는다.** 테스트로 확인했다 — 502 응답에
`openai down` 같은 문구가 섞이지 않는다.

## 4. 쓰기 경로도 만료를 막는다

조회만 막으면 충분하지 않다. 만료된 사건에 답변을 제출할 수 있으면 `pg_cron`이 지운 뒤에
새 데이터가 들어와 되살아난다. `_active()` 헬퍼가 조회와 쓰기 양쪽에서 같은 검사를 한다.

## 5. 권한 — A만 요구하고 B는 요구하지 않는다

| 엔드포인트 | `X-Writer-Token` |
| --- | --- |
| `statement` (side A) | **필수.** 없으면 403 |
| `statement` (side B) | 불필요 |
| `response-type` | 불필요 |
| `apology` | 불필요 |

B에게 토큰을 요구하면 "링크 하나로 전달이 끝난다"는 구조가 깨진다. B의 중복 제출은 토큰이
아니라 §2의 조건부 UPDATE와 DB 제약이 막는다.

## 6. 테스트가 잡은 것 — 공백만 있는 사과문

`Field(min_length=1)`로는 `"   "`가 통과한다. 프론트는 `!value.body.trim()`으로 막고 있었는데
서버는 안 막고 있었다. `StringConstraints(strip_whitespace=True, min_length=1)`로 고쳤다.

프론트만 막고 서버가 안 막으면 API를 직접 호출하는 경로에서 빈 사과문이 저장된다.

## 7. 검증

| 항목 | 결과 |
| --- | --- |
| `ruff check` | 통과 |
| `unittest` 72개 | 통과 |
| 실DB 전체 흐름 14단계 | 통과 |
| 실DB 동시 제출 (스레드 8개 × 3종) | 통과 |

실DB 검증은 `postgres:17` 컨테이너에 마이그레이션 4개를 적용해 운영과 같은 구조를 만들고
목 없이 돌렸다. 확인한 것 중 목으로는 잡히지 않는 것들:

- 맞고소 완료 시 `expires_at`이 **`answered_at` 기준 +7일**로 갱신되는가
- 중재 리포트의 `hurt_points_a/b`가 각 측 `emotions[]`를 그대로 담는가
- 사과 경로에는 중재 리포트가 **생기지 않는가**
- 잘못된 순서(A 제출 전 응답 선택, `DRAFT`에서 사과문)가 409인가
- 만료 후 **쓰기**가 410인가

## 9. 배포 배선 — 반나절을 쓴 사고와 그 정리

`docker-compose.yml`에 `env_file`을 넣었는데도 운영 AI가 폴백으로 돌고 사건 API가 503을
냈다. 원인이 **두 겹**이었다.

### 9.1 `.env`가 두 개인데 엉뚱한 쪽을 가리켰다

```
~/services/202609_wantedHackathon/.env          ← env_file이 보던 곳. 키 없음
~/services/202609_wantedHackathon/backend/.env  ← 키가 있던 곳
```

`env_file`은 **compose 파일 기준 상대경로**다. `env_file: .env`는 루트를 가리켰는데 키는
`backend/.env`에 있었다. `./backend/.env`로 고쳤다.

Compose가 `.env`를 읽는 방식이 두 가지이고 서로 다르다는 점이 함정이었다.

| 역할 | 파일 | 대상 |
| --- | --- | --- |
| `${VIRTUAL_HOST}` **치환** | 루트 `.env` (자동) | compose 파일 자체 |
| 컨테이너 **안으로** 주입 | `env_file`이 가리키는 파일 | 컨테이너 |

루트 `.env`에 키를 넣어도 컨테이너는 보지 못한다.

### 9.2 `docker compose up -d`만으로는 이미지가 갱신되지 않는다

첫 사고를 고치는 과정에서 두 번째 사고가 났다. 서버에서 `up -d`만 실행했더니 **API 경로가
`/api/health` 하나로 줄어든 상태로 운영됐다.**

`image: ...:${IMAGE_TAG:-latest}`이므로 `IMAGE_TAG` 없이 `up -d`만 하면 서버에 있던 옛
`:latest`가 그대로 뜬다. CD는 `export IMAGE_TAG=<sha>` 후 `pull`까지 하므로 정상이었는데,
수동 재기동에서 그 두 단계가 빠졌다. **안내에서 `docker compose pull`을 뺀 것이 원인이었다.**

### 9.3 진단에 쓴 신호

응답 **문구**가 원인을 갈랐다.

| 응답 | 의미 |
| --- | --- |
| `404 {"detail":"Not Found"}` | FastAPI 기본값 — **라우트 자체가 없음** (옛 이미지) |
| `404 {"detail":"Case not found"}` | 우리 코드 — 라우트 존재, **DB 질의까지 성공** |
| `503 {"detail":"Storage unavailable"}` | `DATABASE_URL`이 빈 값 |
| 대화 API `mode: "local"` | `OPENAI_API_KEY`가 빈 값 |

대문자 `Not Found`와 우리 문구를 구별하는 것이 "이미지가 옛것인가, 환경변수가 없는가"를
가르는 결정적 신호였다. 오류 문구를 서로 다르게 쓴 것이 진단을 빠르게 했다.

### 9.4 최종 확인

```
경로 8개 전부 배포됨
GET /api/cases/xxx  → 404 {"detail":"Case not found"}
대화 API            → mode: openai
POST /api/cases     → 201, DRAFT, expires_at 7일 뒤, 토큰 2개
```

프로덕션 DB에 실제로 행이 들어가고 읽히는 것까지 확인했다. 만들어진 빈 사건은 7일 뒤
`pg_cron`이 정리한다.

### 9.5 CD를 고쳐 재발을 막았다

문제의 뿌리는 **서버 설정이 레포와 조용히 어긋날 수 있다는 것**이었다. CD가 이미지만
갱신하고 `docker-compose.yml`은 사람이 직접 `git pull` 해야 했다.

배포 스크립트가 서버를 `origin/main`으로 강제 동기화하게 했다.

```bash
git fetch origin main
git reset --hard origin/main
```

**원칙 — 서버는 `main`의 거울이다.** 추적 파일은 어디서나 동일하고, 서버마다 다른 값은
`.env`로만 표현한다. 서버에서 추적 파일을 직접 고치면 다음 배포에 버려진다.

`.env`는 `.gitignore` 대상이라 `reset --hard`가 건드리지 않는다.

`git pull` 대신 `reset --hard`를 쓴 이유는, pull은 서버에 미커밋 수정이 있으면 배포가
멈추고 서버에서 커밋해뒀다면 충돌까지 나기 때문이다. 배포 파이프라인에서 겪고 싶은 일이
아니다. 파괴적이지만 원칙을 코드로 강제한다.

배포 후 `docker compose ps`로 실제로 뜬 이미지를 로그에 남겨 9.2 같은 사고를 빨리
발견하게 했다.

`docs/Tech_ADR.md`에 §11(배포 환경변수)·§12(서버는 main의 거울)로 기록했다.

## 10. 문서 감사 — 스키마 진실이 세 곳에서 어긋나 있었다

구현이 빠르게 진행되면서 문서가 코드·DB를 따라오지 못했다. 마이그레이션에서 실제 컬럼을
뽑아 문서와 대조했다.

### 10.1 발견

| 문서 | 상태 |
| --- | --- |
| `PRD.md` §11 | **7개 필드를 모름** — `writer_token_hash`, `answered_at`, `purged_at`, `hurt_point`, `expected_behavior`, `assumption`, `admitted_point` |
| `Supabase_Schema_Design.md` §4 | DDL 블록이 **최초 설계 그대로**. 추가된 5개 컬럼은 §7에만 있어, §4만 읽으면 잘못된 그림을 얻음 |
| `Data_Flow.md` §3 | `cases` 필드 목록에 `writer_token_hash` 없음. §11 구현 매핑이 옛 구조 |

§4가 특히 위험했다. 그 절은 "테이블이 이렇게 생겼다"는 **기준 문서** 역할을 하는데, 실제와
다른 DDL을 보여주고 있었다. 새 팀원이 그것만 보고 코드를 짜면 어긋난다.

### 10.2 고친 방식

**추가된 컬럼을 원래 DDL 안에 넣고 주석으로 시점을 남겼다.** §7의 마이그레이션 목록과
중복되지만, 두 절의 목적이 다르다 — §4는 "지금 테이블이 어떻게 생겼나", §7은 "어떤 순서로
그렇게 됐나". 전자를 보러 온 사람이 후자까지 읽어야 한다면 기준 문서가 아니다.

PRD §11은 제목을 "데이터 구조 **초안**"에서 "데이터 구조"로 바꾸고, 초안 이후 추가된
필드를 **굵게** 표시했다. 어떤 것이 기획에서 왔고 어떤 것이 구현에서 왔는지 구분된다.

`Data_Flow.md`는 v0.4로 올리고 §11 구현 매핑을 실제 모듈 경로로 갱신했다.

### 10.3 새로 드러난 미결 — `pg_cron`이 실제로 도는가

문서를 맞추다 보니 **한 번도 확인하지 않은 것**이 보였다. 만료 배치 잡은 등록했지만
`cron.job_run_details`를 본 적이 없다.

7일 뒤 삭제는 이 제품의 핵심 약속인데(`Data_Flow.md` §2-5 "만료는 열람 차단이 아니라
데이터 소멸"), **잡이 돌지 않아도 증상이 드러나지 않는다.** lazy 검사가 열람을 막아주기
때문이다. 사용자 눈에는 정상으로 보이고 데이터만 남는다.

`API_Design.md` §10-10으로 올렸다. 확인은 SQL 두 줄이면 된다.

```sql
select jobname, schedule, active from cron.job;
select status, start_time, return_message
  from cron.job_run_details order by start_time desc limit 5;
```

| 문서 | 권위를 갖는 범위 |
