# 2026-09-14 진행상황

API 계약을 문서화하고, 그 문서를 **실제 구현에 맞춰 개정**했다. 그 과정에서 API·프론트·DB가
같은 데이터를 서로 다른 형태로 다루고 있다는 것이 드러나 통일 방향을 결정했다.

작업 브랜치: `docs/api-design` → `docs/api-design-sync` → `docs/card-shape-decision`

---

## 1. API 설계 문서 최초 작성

`Frontend_Architecture.md` §9가 "필요한 계약"으로 나열만 해둔 7개 항목에 실제 경로·요청·
응답·오류 코드를 부여했다. 설계 결정 다섯 가지를 정했다.

| # | 결정 |
| --- | --- |
| A-1 | AI 대화는 무상태 — 서버가 대화를 보관하지 않음 |
| A-2 | 리포트 생성은 동기 |
| A-3 | A의 쓰기 권한은 별도 `writer_token` |
| A-4 | AI 응답은 비스트리밍 |
| A-5 | 전이 가능 여부를 서버가 `available_actions`로 전달 |

이 시점에는 백엔드에 `health.py`밖에 없다고 보고 설계했다. **이 전제가 틀렸다 — §2 참고.**

## 2. 소스를 읽어보니 이미 구현돼 있었다

설계 문서를 머지한 뒤 소스를 확인했더니, 09-12~09-14 사이에 팀원들이 백엔드를 구현해둔
상태였다(PR #7, #8). 설계 문서와 구현이 **서로를 모르는 채로 각각 만들어졌다.**

```
backend/app/
  api/conversation.py    POST /api/complaint/conversation/message
  api/mediation.py       POST /api/mediation/report
  services/complaint_engine.py   (1,125줄)
  services/mediation.py
  services/openai_gateway.py
```

프론트도 이미 연결돼 있었다. `frontend/src/lib/api/{conversation,mediation}.ts`가
어댑터 역할을 하고 `useConversation.ts`·`MediationSummary.tsx`가 이를 통해 호출한다.
`Frontend_Architecture.md` §9의 "화면 컴포넌트에서 직접 fetch를 흩어 쓰지 않는다"가
지켜지고 있다.

### 2.1 문서가 틀렸던 것

| 문서 | 실제 |
| --- | --- |
| `POST /api/cases/{token}/conversation` | `POST /api/complaint/conversation/message` |
| 대화 원문 전체 재전송 | **구조화 상태 객체 왕복** |
| 필드명 snake_case | camelCase alias (`assistantMessage`, `readyToGenerate`) |
| 리포트는 `statement`가 겸함 | **독립 엔드포인트** |

두 번째는 **구현이 설계보다 낫다.** 설계는 대화 원문 전체를 매 요청에 재전송하는 방식이었는데,
구현은 최신 메시지 하나와 누적된 구조화 상태만 주고받는다. 원문이 서버에 도달하는 것이
한 번뿐이라 DFD §2-2 "원문은 흐르되 고이지 않는다"를 더 좁은 통로로 만족시킨다.

### 2.2 코드가 이미 하고 있던 것

설계 문서가 "구현이 책임져야 한다"고 적은 원문 비저장 장치 대부분이 이미 들어가 있었다.

- 422 전역 핸들러가 입력값 에코 차단 (`{"detail": "Invalid request"}` 고정)
- `raise ... from None`으로 provider 예외 체인 차단
- 대화·리포트 응답에 `Cache-Control: no-store`
- OpenAI 호출에 **`store=False`**, 타임아웃 25초, 재시도 0회
- `enforce_single_question()`이 FR-02(한 번에 하나의 질문)를 후처리로 강제

특히 `mediation.ground_report()`가 인상적이다. LLM 응답을 받은 뒤 `different_views`·
`hurt_points_a/b`를 **입력값으로 강제 치환**하고 `possible_misunderstanding`을 항상
`null`로 고정한다. 코드 주석이 이유를 남겼다.

> Free-form causal inference can silently reverse A/B even with role prompts.
> Until source/actor grounding is available, do not publish this speculation.

PRD §13 "AI가 하지 않아야 하는 일"을 프롬프트가 아니라 코드로 강제한 것이다.

### 2.3 연쇄 갱신

- `Tech_ADR.md` 미해결에서 **LLM 제공자** 항목을 내렸다 → OpenAI `gpt-4.1-mini`
- `Data_Flow.md` **v0.3** — `store=False` 적용으로 §7.1 외부 AI 제공자 보관 정책이
  해소돼 미결이 4건에서 3건으로 줄었다

## 3. 카드 형태 통일 — DB 기준으로 결정

같은 "고소장 카드"를 세 곳이 다르게 표현하고 있었다.

| 어디 | 필드 |
| --- | --- |
| DB `statement_cards` | `cute_charge`, `incident_summary`, `incident_description`, `emotions[]`, `emotion_reason`, `different_viewpoint`, `desired_outcome` |
| API `SharedStatement` | `incident`, `feeling`, `wish`, `expectation`, `guess` |
| 프론트 `Statement` | 위와 동일 |

**DB를 기준으로 통일하기로 했다.** PRD §11에서 온 형태라 제품 기획에 가장 가깝고,
`cute_charge`(귀여운 죄명) 같은 제품 핵심 요소가 DB에만 있기 때문이다.

### 3.1 단순한 이름 변경이 아니다

처음에는 "API·프론트를 DB 이름으로 바꾸면 끝"이라고 봤으나, 확인해보니 아니었다.

`expectation`·`guess`는 **이미 동작하는 기능**이다. `ShareSelectScreen.tsx`가 사용자에게
이 둘을 공유할지 고르게 하고 `StatementCard.tsx`가 카드에 표시한다. 사과문의 `admitted`도
마찬가지다. 버리면 기능 후퇴다.

따라서 "DB 기준"은 **DB가 이름과 구조의 권위를 갖되, 프론트에만 있던 항목은 마이그레이션으로
DB가 흡수한다**는 뜻이 된다. 컬럼 세 개를 추가해야 한다.

### 3.2 감정 목록이 유실되고 있었다

대화 상태(`ComplaintConversationState.emotion`)는 이미 `{emotions[], reason}`으로 DB와
정확히 같은 모양이다. 그런데 이를 카드로 옮기는 `SharedStatement`가 `feeling` 한 덩어리로
납작하게 만들면서 **감정 목록이 통째로 버려지고 있었다.** 기준 형태로 옮기면 자동으로
해소된다.

### 3.3 아직 아무도 만들지 않는 필드 셋

`cute_charge`·`incident_summary`·`different_viewpoint`는 **어디에서도 생성되지 않는다.**
`complaint_engine`의 추출 항목에 없다. 카드를 저장하려면 대화 엔진을 확장하거나 저장 시점에
별도 LLM 호출을 넣어야 한다. 미결로 남겼다.

### 3.4 예정 마이그레이션

```sql
-- <타임스탬프>_align_api_schema.sql
alter table cases           add column writer_token_hash text;  -- A-3
alter table statement_cards add column expected_behavior text;  -- 현 expectation
alter table statement_cards add column assumption        text;  -- 현 guess
alter table apologies       add column admitted_point     text;  -- 현 admitted
```

넷 다 nullable, 백필 불필요. **PRD §11 데이터 구조 초안에 없던 필드**이므로 PRD도 함께
갱신하는 것이 맞다.

## 4. 배포 환경변수 배선이 빠져 있다

DB 접속을 어떻게 붙일지 확인하다 발견했다. `docker-compose.yml`의 backend 서비스에
**`OPENAI_API_KEY`도 `DATABASE_URL`도 없다.** 프록시·인증서 관련 변수만 있다.

```yaml
backend:
  environment:
    - VIRTUAL_HOST=${VIRTUAL_HOST}
    - VIRTUAL_PATH=/api/
    - LETSENCRYPT_HOST=${LETSENCRYPT_HOST}
```

`.dockerignore`가 `.env*`를 제외하므로 이미지에도 들어가지 않는다.

코드는 키가 없으면 `mode: "local"`로 빠지게 돼 있다.

```python
def is_openai_configured() -> bool:
    return bool(settings.openai_api_key.strip()) and not settings.conversation_use_local
```

**즉 운영 환경의 AI 대화가 진짜 LLM이 아니라 키워드 규칙 기반 폴백으로 동작하고 있다.**
로컬에서는 `.env`로 잘 되는데 서버에서는 딴판인 상태다. DB 접속 코드를 추가해도
`DATABASE_URL`이 없으면 같은 문제를 겪는다.

`docs/API_Design.md` §10-9에 미결로 올렸다.

## 결정하지 않고 남긴 것

| # | 항목 | 정해야 할 시점 |
| --- | --- | --- |
| 1 | `cute_charge`·`incident_summary`·`different_viewpoint`를 누가 생성할지 | 카드 저장 구현 전 |
| 2 | 오류 응답 형식 — `{detail}` vs `{code, message}` | 사건 계층 착수 전 |
| 3 | 네이밍 규칙 — camelCase vs snake_case가 엔드포인트마다 갈림 | 프론트 연결 전 |
| 4 | 배포 환경변수 배선 방식 | 사건 계층 배포 전 |
| 5 | 동기 응답이 타임아웃 안에 드는지 실측 | 맞고소 경로 연결 시 |
| 6 | 백엔드 DB 접근 계층 선택 | 사건 계층 착수 시 |
| 7 | 개발용 Supabase 프로젝트를 따로 둘지 | DB 연결 전 |

5번은 A-2(동기)의 유일한 실질 위험이다. OpenAI 타임아웃 25초 × 맞고소 경로 2회 =
최악 50초이고 Nginx 기본 `proxy_read_timeout`은 60초다.

7번은 현재 Supabase 프로젝트가 하나뿐이라 **로컬 개발이 운영 DB를 직접 건드리게 된다**는
문제다. 3주 프로젝트라 하나로 써도 되지만 알고 쓰는 것과 모르고 쓰는 것은 다르다.
