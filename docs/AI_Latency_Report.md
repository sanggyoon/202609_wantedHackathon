> 작성일: 2026-09-15 · 담당: Yejin · 관련 작업: 착수 전 결정 검증 "1번 — AI가 얼마나 오래 걸리는지 재보기"
> 관련 문서: [API_Design.md](API_Design.md) §10-5(동기 응답 실측), §5(중재 리포트) · 대상 코드: `backend/app/api/mediation.py`, `backend/app/services/openai_gateway.py`
>

> 호출이 실제로 일어나는 곳은 **대화 API**다(추출 + 발화, 최대 50초). 측정 이후 호출 경로도
> 늘었다 — §9를 참고한다.

## 1. 왜 쟀나 (목적)

맞고소 리포트를 만들 때 백엔드가 OpenAI를 호출한다. 우려는 이거였다:

- OpenAI 호출은 코드상 **1회 최대 25초**로 제한돼 있다. (`openai_gateway.py`: `timeout=25, max_retries=0`)
- 맞고소 완료 흐름은 최악의 경우 이런 호출이 **연달아 2번** → 이론상 최대 **50초**.
- 그런데 배포용 Nginx 기본 타임아웃은 **60초**. 요청이 60초를 넘으면 서버가 **연결을 끊어버린다**.

즉 **50초 vs 60초**로 아슬아슬해 보였다.

**이게 왜 먼저 정해져야 하나:** 만약 실제로 60초에 걸린다면, 지금 설계한 "요청을 받고 기다렸다가 결과를 한 번에 돌려주는(동기)" 방식을 **"일단 접수만 하고 결과는 나중에 알려주는(비동기)"** 방식으로 바꿔야 한다. 이건 뒤따르는 저장·프론트 작업 설계를 전부 바꾸기 때문에, **작업을 시작하기 전에** 실측으로 확인하는 게 가장 싸다.

## 2. 무엇을 / 어떻게 쟀나 (측정 방법)

| 항목 | 내용 |
| --- | --- |
| 측정 대상 | `POST /api/mediation/report` (리포트 생성, OpenAI 실제 호출) |
| 모델 | `gpt-4.1-mini` (`.env`의 `OPENAI_MODEL`) |
| 실행 환경 | 로컬 (`python -m uvicorn app.main:app --port 8000`) |
| 측정 도구 | PowerShell `Measure-Command` (명령 실행에 걸린 실제 시간을 잼) |
| 입력 | 아래 §3의 고정 샘플 1건 (5회 모두 동일 입력 — 변수 통제) |
| 반복 | 5회 |

측정 명령:
```powershell
Measure-Command { Invoke-RestMethod -Uri http://localhost:8000/api/mediation/report `
  -Method Post -ContentType "application/json; charset=utf-8" -InFile ".\sample_report.json" }
```

> 참고: 응답이 실제 OpenAI 호출이었는지(`mode: "openai"`) vs 가짜 로컬 응답(`mode: "local"`)인지도 확인함. 로컬 모드라면 0.1초도 안 걸리는데, 실측이 초 단위로 나온 것 자체가 **진짜 OpenAI를 탔다는 증거**다.

---

## 3. 어떤 데이터를 넣었나 (측정 입력)

5회 모두 **같은 가상 사건 1건**을 넣었다. (같은 입력을 반복해야 순수한 응답 속도 편차를 볼 수 있음)

- **신청인 A**: "저녁 약속에 상대가 한 시간 넘게 늦으면서 연락이 없었다" — 감정: 서운함/걱정/화남, 바라는 점: 늦으면 미리 연락
- **상대방 B**: "회사 일이 길어져 휴대폰을 못 봤다" — 감정: 미안함/답답함, 바라는 점: 서로 상황을 먼저 물어보기

즉 실제 서비스에서 나올 법한 **양측 진술이 다 채워진 리포트 생성 요청**이라, 가벼운 입력이 아니라 현실적인 부하다.

## 4. 결과 지표 각 줄의 뜻

`Measure-Command`가 뱉는 출력의 각 줄 의미:

| 줄 | 뜻 |
| --- | --- |
| `Days` / `Hours` / `Minutes` | 걸린 시간을 일·시·분으로 쪼갠 값 (여기선 전부 0) |
| `Seconds`, `Milliseconds` | 사람이 읽기 쉽게 쪼갠 값. 예: `Seconds:6, Milliseconds:568` → **6초 568밀리초** |
| **`TotalSeconds`** | ⭐ **전체 걸린 시간을 "초" 하나로 합친 값. 우리가 실제로 볼 핵심 숫자.** (예: 6.568) |
| `TotalMilliseconds` | 같은 시간을 밀리초(1/1000초)로. `TotalSeconds`×1000 |
| `TotalMinutes` / `TotalHours` / `TotalDays` | 같은 시간을 분/시/일 단위로 환산 (짧아서 소수점) |
| `Ticks` | 컴퓨터 내부 최소 시간 단위(1틱 = 100나노초). 사람이 볼 필요 없음 |

**핵심:** 여러 줄이지만 전부 "같은 하나의 시간"을 단위만 바꿔 보여주는 것이다. 우리는 **`TotalSeconds`** 하나만 보면 된다.

## 5. 측정 결과

| 회차 | TotalSeconds | 비고 |
| --- | --- | --- |
| 1회 | **6.57초** | 첫 실행(워밍업)이라 가장 느림 |
| 2회 | 3.01초 | |
| 3회 | 2.37초 | 최소 |
| 4회 | 3.19초 | |
| 5회 | 2.76초 | |

- **최대: 6.57초** (첫 실행 워밍업 포함)
- **최소: 2.37초**
- **평균: 약 3.58초**
- **워밍업 제외한 안정 구간(2~5회): 2.4 ~ 3.2초**

첫 회가 느린 건 서버·연결이 처음 데워지는 **워밍업** 때문이며, 이후엔 3초 안팎으로 안정적이다.

## 6. 해석 및 평가

1회 호출의 실제 시간을 근거로, 최악 시나리오(2회 연속)를 **보수적으로** 추정한다.

| 시나리오 | 추정 시간 | 서버 컷(60초) 대비 |
| --- | --- | --- |
| 실측 1회 (최대) | 6.6초 | — |
| 최악 2회 연속 (실측 최대 ×2) | **약 13초** | 여유 약 47초 ✅ |
| 코드상 하드 상한 (25초 ×2) | 50초 | 그래도 60초 미만 |

- 현실 시간은 **약 13초**로, 60초 컷과 비교하면 **여유가 대단히 크다.**
- 설령 네트워크가 느려 최악의 하드 상한(50초)에 걸려도 60초는 넘지 않는다.
- 응답이 초 단위로 걸린 것으로 보아 **실제 OpenAI 호출이 정상 동작**함을 확인했다.

## 7. 결론 및 권고

- ✅ **"기다렸다 한 번에 돌려주는(동기)" 방식을 그대로 유지해도 된다.**
- ✅ **비동기(접수 후 나중에 알림) 재설계는 지금 불필요하다.** → 뒤따르는 저장·프론트 작업을 원래 설계대로 진행 가능.

## 8. 한계 및 주의 (솔직한 전제)

- 현재 `mediation/report` 코드는 OpenAI를 **실제로는 1회** 호출한다. "×2(최악 50초)"는 맞고소 완료 흐름에서 발생할 수 있는 **2회 연속 호출을 가정한 보수적 추정**이며, 그 2회 흐름은 아직 완성 전이다. 완성 후 실제 2회 연속 시간을 다시 실측하면 더 정확하다.
- 로컬·단일 네트워크 기준 측정이다. 배포 서버·해외 리전·트래픽 몰림 시 더 느려질 수 있으나, 13초 → 60초의 여유가 커서 판단이 뒤집힐 가능성은 낮다.
- 입력 길이가 크게 길어지면(진술이 매우 김) 토큰이 늘어 시간이 증가할 수 있다.

## 9. 2026-09-19 기준 현황 (측정 이후 변화)

측정 당시에는 OpenAI 호출 경로가 대화와 리포트뿐이었다. 지금은 다섯 곳이다.

| 경로 | 호출 수 | 코드 |
| --- | --- | --- |
| 대화 1턴 | **2회 연속** (추출 + 발화) | `services/complaint_engine.py` |
| 카드 요약 (죄명·한 줄 요약·도입문) | 1회 | `services/card_summary.py` |
| 감정 프로파일 채점 | 1회 | `services/emotion_profile.py` |
| 중재 리포트 | 1회 | `services/mediation.py` (B 맞고소 제출 시 `api/cases.py`가 호출) |

`/api/mediation/report`를 직접 부르는 화면은 체험용 `/wireframe`뿐이다.

클라이언트 타임아웃도 서버 컷(Nginx 60초)과 함께 봐야 한다.

| 경로 | 클라이언트 제한 |
| --- | --- |
| 대화 | 55초 (`useConversation.ts`) — Nginx 60초 컷보다 먼저 끊어 재시도 안내를 보여준다 (2026-09-19 조정) |
| 중재(체험) | 35초 (`MediationSummary.tsx`) |
| 감정 프로파일·이미지 | 30초 / 제한 없음 (`lib/api/emotionWarp.ts`) |
| 사건 저장 (B 맞고소) | 60초 (`lib/api/cases.ts`) |

**남은 점검:** 대화 API는 한 요청에서 AI를 2회 연속 부르므로 최악 50초다. 클라이언트는 55초에서
끊도록 맞췄지만, 서버 `proxy_read_timeout`(기본 60초)을 90초 정도로 올릴지는 운영 실측 후 정한다.
